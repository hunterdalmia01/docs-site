01

Introduction to FastAPI

#1 · 3:53

FastAPI is a modern Python web framework for building APIs, built on top of Starlette (the ASGI toolkit that handles routing and async request/response) and Pydantic (data validation via Python type hints). Its selling points:

  • Speed — one of the fastest Python frameworks, comparable to Node.js/Go, because it's built on ASGI (async) rather than WSGI.
  • Type hints do the work — function signatures double as validation rules, so request bodies, query params, and responses are checked automatically.
  • Free interactive docs — Swagger UI (/docs) and ReDoc (/redoc) are generated from your code, no extra tooling.
  • Async-native — async def endpoints handle high-concurrency I/O (DB calls, external APIs) efficiently.
Where it fits: Flask-like simplicity, Django-REST-like structure for larger apps, but faster and with validation built in rather than bolted on.

04

Path parameters & query parameters

#4 · 26:02

Path parameters are part of the URL and identify a specific resource. Query parameters come after ? and are for optional filters, sorting, pagination.

# path parameter — type-hinted as int, FastAPI validates & converts it
@app.get("/items/{item_id}")
def get_item(item_id: int):
    return {"item_id": item_id}

# query parameters — plain function args with defaults are query params
@app.get("/items/")
def list_items(skip: int = 0, limit: int = 10, q: str | None = None):
    return {"skip": skip, "limit": limit, "q": q}
Ordering matters: a fixed path like /items/latest must be declared before /items/{item_id}, or FastAPI will try to parse "latest" as the item_id type and fail.

Because item_id: int is enforced automatically, calling /items/abc returns a 422 Unprocessable Entity with a descriptive error — no manual validation code needed.

Each maps to a decorator: @app.get, @app.post, @app.put, @app.delete. The method is a contract about intent and safety (can it be retried without side effects?), not just a routing label.

06

POST, PUT, DELETE + Pydantic validation

#6 · 38:06

Request bodies are defined as Pydantic models — a class with typed fields. FastAPI parses incoming JSON into the model, validates every field, and rejects bad input before your function body even runs.

from pydantic import BaseModel

class Item(BaseModel):
    name: str
    price: float
    in_stock: bool = True

@app.post("/items/")
def create_item(item: Item):
    return {"created": item}

@app.put("/items/{item_id}")
def update_item(item_id: int, item: Item):
    return {"item_id": item_id, "updated": item}

@app.delete("/items/{item_id}")
def delete_item(item_id: int):
    return {"deleted": item_id}
Pydantic turns "validate this input" from imperative if-checks into a declared shape. Wrong type, missing required field, or extra constraints (via Field(...)) all produce a clean 422 automatically.

Project setup & folder structure

#7 · 13:40

A single main.py doesn't scale. The common FastAPI layout separates concerns so routes, DB logic, and schemas don't tangle:

app/
├── main.py          # creates FastAPI(), includes routers
├── database.py      # engine, SessionLocal, Base
├── models.py         # SQLAlchemy ORM models (DB tables)
├── schemas.py        # Pydantic models (request/response shapes)
├── routers/
│   ├── items.py
│   └── users.py
└── utils/ (hashing, auth helpers, email, ...)

Key distinction that trips people up: models.py describes database tables (SQLAlchemy), schemas.py describes the JSON shapes going in/out over HTTP (Pydantic). They often look similar but serve different layers.

Connect PostgreSQL with SQLAlchemy

#8 · 11:03
pip install sqlalchemy psycopg2-binary
# database.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

DATABASE_URL = "postgresql://user:password@localhost:5432/mydb"

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

get_db is a dependency — FastAPI's own DI system. Declaring db: Session = Depends(get_db) in a route hands it a fresh session per request and guarantees cleanup, even on error.

10

POST endpoint with database — insert data

#10 · 21:04
from fastapi import Depends
from sqlalchemy.orm import Session

@app.post("/items/")
def create_item(item: schemas.ItemCreate, db: Session = Depends(get_db)):
    db_item = models.Item(**item.dict())
    db.add(db_item)
    db.commit()
    db.refresh(db_item)   # pulls back generated fields, e.g. id
    return db_item

The flow is always the same for a write: build the ORM object → add → commit → refresh (to get the DB-generated id back into the Python object before returning it).

12

GET a specific record by ID

#12 · 11:17
from fastapi import HTTPException

@app.get("/items/{item_id}")
def get_item(item_id: int, db: Session = Depends(get_db)):
    item = db.query(models.Item).filter(models.Item.id == item_id).first()
    if not item:
        raise HTTPException(status_code=404, detail="Item not found")
    return item
This is the template for "fetch or 404" everywhere in a FastAPI app: query with a filter, check for None, raise HTTPException if missing. FastAPI converts that exception straight into the right JSON error response.
13

Update & delete — complete CRUD

#13 · 14:18
@app.put("/items/{item_id}")
def update_item(item_id: int, updated: schemas.ItemCreate, db: Session = Depends(get_db)):
    item = db.query(models.Item).filter(models.Item.id == item_id).first()
    if not item:
        raise HTTPException(status_code=404, detail="Item not found")
    for key, value in updated.dict().items():
        setattr(item, key, value)
    db.commit()
    db.refresh(item)
    return item

@app.delete("/items/{item_id}")
def delete_item(item_id: int, db: Session = Depends(get_db)):
    item = db.query(models.Item).filter(models.Item.id == item_id).first()
    if not item:
        raise HTTPException(status_code=404, detail="Item not found")
    db.delete(item)
    db.commit()
    return {"message": "deleted"}

With this, the four CRUD verbs (Create / Read / Update / Delete) are all covered end to end against a real database — the shape every resource-based API repeats.

14

Production-ready practices

#14 · 15:43
  • Routers — split endpoints with APIRouter() per resource, then app.include_router(items.router, prefix="/items", tags=["items"]) in main.py.
  • Response models — declare response_model=schemas.ItemOut on routes so you never leak internal fields (password hashes, etc.) by accident.
  • Status codes — set them explicitly: @app.post(..., status_code=201) for creation, 204 for delete-with-no-body.
  • Environment config — pull secrets and the DB URL from environment variables (e.g. via python-dotenv or Pydantic's BaseSettings), never hardcode them.
  • Consistent error handling — centralize common checks (get-or-404) into small helper functions instead of repeating them per route.

Authentication & authorization — JWT & security overview

#15 · 8:18

Two different questions an API has to answer: authentication ("who are you?") and authorization ("are you allowed to do this?"). The standard modern pattern is:

  1. User registers → password is hashed, never stored in plain text.
  2. User logs in with credentials → server verifies the hash → issues a JWT (JSON Web Token).
  3. Client sends that JWT on every subsequent request (Authorization: Bearer <token>).
  4. Protected routes decode/verify the token via a dependency instead of re-checking a password each time.

Libraries used across the playlist: passlib[bcrypt] for hashing, python-jose (or pyjwt) for encoding/decoding JWTs.

16

User registration — password hashing

#16 · 15:19
pip install passlib[bcrypt]
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)

@app.post("/register")
def register(user: schemas.UserCreate, db: Session = Depends(get_db)):
    db_user = models.User(
        email=user.email,
        hashed_password=hash_password(user.password),
    )
    db.add(db_user)
    db.commit()
    db.refresh(db_user)
    return db_user
Never store raw passwords — bcrypt hashing is one-way and salted, so even a DB breach doesn't expose usable credentials.

Registration part 2 — validation & error handling

#17 · 10:35
  • Use Pydantic's EmailStr (via the email-validator package) to validate email format at the schema level.
  • Add a min_length constraint on passwords with Field(min_length=8).
  • Check for duplicate accounts before insert: query by email first, and raise HTTPException(400, "Email already registered") if found — catching the DB's unique-constraint error is a fallback, not the primary check.
class UserCreate(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8)
18

Login API — JWT tokens

#18 · 16:21
from jose import jwt
from datetime import datetime, timedelta

SECRET_KEY = "change-me"     # load from env in real apps
ALGORITHM = "HS256"

def create_access_token(data: dict, expires_minutes: int = 30):
    to_encode = data.copy()
    to_encode["exp"] = datetime.utcnow() + timedelta(minutes=expires_minutes)
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

@app.post("/login")
def login(form: schemas.LoginRequest, db: Session = Depends(get_db)):
    user = db.query(models.User).filter(models.User.email == form.email).first()
    if not user or not verify_password(form.password, user.hashed_password):
        raise HTTPException(status_code=401, detail="Invalid credentials")
    token = create_access_token({"sub": user.email})
    return {"access_token": token, "token_type": "bearer"}

The token's payload (sub, short for "subject") identifies the user; exp makes it expire automatically. The token is signed, not encrypted — never put secrets inside it, since anyone can decode the payload.

19

Token-based authentication — securing endpoints

#19 · 19:38
from fastapi.security import OAuth2PasswordBearer
from jose import JWTError

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="login")

def get_current_user(token: str = Depends(oauth2_scheme), db: Session = Depends(get_db)):
    credentials_exception = HTTPException(status_code=401, detail="Could not validate credentials")
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        email: str = payload.get("sub")
        if email is None:
            raise credentials_exception
    except JWTError:
        raise credentials_exception

    user = db.query(models.User).filter(models.User.email == email).first()
    if user is None:
        raise credentials_exception
    return user

OAuth2PasswordBearer tells FastAPI's docs UI how to collect the token (it adds an "Authorize" button) and extracts the Authorization: Bearer ... header automatically for you.

Protected routes

#20 · 11:21
@app.get("/me")
def read_current_user(current_user: models.User = Depends(get_current_user)):
    return current_user

This is the payoff of the whole auth chain: any route that lists Depends(get_current_user) in its signature is automatically locked behind a valid JWT — a request with no token, an expired one, or a tampered one is rejected with 401 before the route body ever runs.

Table relationships — one-to-many

#21 · 20:48
from sqlalchemy import ForeignKey
from sqlalchemy.orm import relationship

class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    email = Column(String, unique=True)
    tasks = relationship("Task", back_populates="owner")

class Task(Base):
    __tablename__ = "tasks"
    id = Column(Integer, primary_key=True)
    title = Column(String)
    owner_id = Column(Integer, ForeignKey("users.id"))
    owner = relationship("User", back_populates="tasks")

One User row can own many Task rows. The ForeignKey lives on the "many" side (Task.owner_id); relationship() on both classes lets you navigate the link in Python (user.tasks, task.owner) without writing joins by hand.

22

User-owned tasks

#22 · 11:28
@app.post("/tasks/")
def create_task(
    task: schemas.TaskCreate,
    db: Session = Depends(get_db),
    current_user: models.User = Depends(get_current_user),
):
    db_task = models.Task(**task.dict(), owner_id=current_user.id)
    db.add(db_task)
    db.commit()
    db.refresh(db_task)
    return db_task

@app.get("/tasks/")
def list_my_tasks(
    db: Session = Depends(get_db),
    current_user: models.User = Depends(get_current_user),
):
    return db.query(models.Task).filter(models.Task.owner_id == current_user.id).all()

Combining the auth dependency with the relationship from the previous video: every create/list is automatically scoped to the logged-in user, so one user can never see or create records under someone else's account.

Sending emails

from fastapi_mail import FastMail, MessageSchema, ConnectionConfig

conf = ConnectionConfig(

async def send_welcome_email(to: str):
    message = MessageSchema(
        subject="Welcome!",
        recipients=[to],
        body="Thanks for signing up.",
        subtype="html",
    )
    await FastMail(conf).send_message(message)
Gmail requires an App Password (from Google Account → Security → 2-Step Verification), not your account password, once 2FA is enabled.
24

Background tasks

#24 · 6:00

Sending an email inline makes the client wait for SMTP round-trip time. FastAPI's BackgroundTasks defers work until after the response has already been sent:

from fastapi import BackgroundTasks

@app.post("/register")
def register(
    user: schemas.UserCreate,
    background_tasks: BackgroundTasks,
    db: Session = Depends(get_db),
):
    db_user = create_user_in_db(db, user)
    background_tasks.add_task(send_welcome_email, db_user.email)
    return db_user   # client gets this instantly — email sends after
Good for: emails, logging, cache warming, webhooks — short, fire-and-forget jobs. For heavy or long-running work (video processing, bulk data jobs), reach for a real task queue like Celery or ARQ instead; background tasks run in-process and don't survive a server restart.
