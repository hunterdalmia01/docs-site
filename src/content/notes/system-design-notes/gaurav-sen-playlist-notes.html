System Design Primer: How to Start with Distributed Systems?

The whole video runs on a single extended analogy: a pizza shop standing in for a server. Nearly every core distributed-systems term gets introduced as something the shop owner would naturally do to keep up with more customers, before the formal name is attached to it.

The video's whole arc in one line: one chef → a backup chef → specialized chef teams → a central router picking the fastest shop.

Terms introduced through the analogy

Vertical scaling
Paying/upgrading the one chef to work harder — not hiring anyone new.
Horizontal scaling
Hiring more chefs of similar skill — more machines instead of a bigger one.
Single point of failure
One chef getting sick halts the entire shop.
Master–slave
A backup chef standing by — maps directly onto backup DB replicas.
Microservices
Splitting chefs into specialized teams (pizza vs. garlic bread) that scale independently.
Load balancer
A "central authority" that routes orders using real-time metrics, not blind guessing.
Decoupling
Delivery agents separated from the shops — neither needs to know the other's internals.

Worked example — routing by total time, not distance: Shop 1 totals 1hr queue + 5min prep + 10min delivery = 1hr 15min. Shop 2 totals 1hr 5min. The load balancer should route to Shop 2 even if it isn't the nearest — because total time, not proximity, is what matters.

Other details worth keeping

Pre-making dough at 4am during off-peak hours = pre-computation/caching before demand hits. Amazon's evolution from parcel-only to general delivery is used as a real example of a decoupled system extending to new "product types" without redesign. Event logging ("what happened, what's next") is framed as necessary observability — the only way to detect a degrading oven or a broken delivery bike before it becomes an outage.

027:56

System Design Basics: Horizontal vs. Vertical Scaling

The formal treatment of the same choice: scalability, resilience, and consistency are named as the three pillars in permanent tension, and every scaling decision trades between them.

Vertical scalingHorizontal scaling
MoveBuy a bigger machineBuy more machines
CommunicationInterprocess (fast, local)RPC over the network (slower)
ConsistencyStrong, straightforwardRequires "loose transactional guarantees" — dirty reads/writes become a real risk
CeilingHard hardware limitNone — add machine N+1 anytime
ResilienceStill a single point of failureOne node's failure reroutes elsewhere

Consistency-risk example: data passed 3→4, then 4→5, then 5→1 across horizontally scaled nodes — each hop is a chance for the chain to fall out of sync, which is exactly why horizontal systems settle for looser guarantees.

The realistic answer

Production systems are almost always a hybrid: scale each individual machine vertically as large as budget allows, then scale horizontally by adding more of those machines. Early-stage systems lean vertical (simplicity); horizontal scaling gets adopted as user trust and load grow.

0313:50

What Is Load Balancing?

Introduces the simplest possible routing scheme — hash the request ID, then mod by the number of servers — and then shows exactly how it breaks the moment the server count changes.

Adding one server to a 4-server modulo scheme reshuffles the majority of the keyspace — "almost all of it is useless now" (every cached per-user entry moves to a new server).

Terms

Request ID
A uniformly random identifier per request, often embedding the user ID so the same user always lands on the same server.
Load factor
Expected load per server = 1/N under uniform hashing.
Keyspace
The full range of possible hash values (0 to M−1).
Cache invalidation
When a server assignment changes, that server's cached per-user data is now useless.

The desired property this scheme fails to deliver: adding a 5th server to a 4-server fleet should ideally move only ~20% of total load ("take a little from this server, a little from that one") — not reshuffle the whole system. That gap is exactly what Video 4 (Consistent Hashing) fixes.

Algorithms named: round-robin, least-connections, weighted distribution. Also called a "reverse proxy." Health checks poll each server periodically and stop routing to unresponsive ones.

0410:50

What Is Consistent Hashing and Where Is It Used?

Replaces the linear hash-mod-N scheme with a circular hash ring — both servers and requests are hashed onto the same ring (0 to M−1, wrapping around), and each request routes to the nearest server going clockwise.

Adding S5 only affects the arc between S4 and S1 — S2, S3, and their requests are completely untouched. Contrast with Video 3's full reshuffle.

Virtual nodes fix uneven load

With too few physical servers on the ring, load can still skew badly — "about half the load" landing on one server in the video's example. Fix: hash each physical server through K different hash functions (H1, H2, H3…), placing it at K points around the ring instead of one. Recommended K ≈ log(n). A server crashing then only affects K small arcs spread around the ring, not one big one.

Server crash
Its requests simply move to the next clockwise server — minimal, localized impact.
Named applications
Web caches, distributed databases, general distributed-system load balancing.
059:59

What Is a Message Queue and Where Is It Used?

Builds up every responsibility a task queue must handle, piece by piece, via a pizza-chain analogy: accept tasks asynchronously, persist them, assign them, detect failure, and reassign safely without duplicating work.

Server 3 crashes holding orders 9 & 11. A 15-second heartbeat detects it, and — using consistent hashing buckets from Video 4 — only Server 3's buckets get reassigned, so an order already safely running on Server 2 is never duplicated.

The duplication bug this design avoids

Naive recovery ("just re-query anything marked incomplete and reassign it") can duplicate work: Order 3 is already processing on Server 2 but still marked incomplete in the DB, so it gets mistakenly reassigned to Server 1 too — two pizzas made, one customer, wasted cost. The fix reuses Video 4's consistent-hashing bucket ownership: each server owns a defined bucket range, so a crash only redistributes that server's buckets, not the whole queue.

Named implementations: RabbitMQ, ZeroMQ, JMS (Java Messaging Service).

What Is a Microservice Architecture and What Are Its Advantages?

"There's nothing micro about a microservice" — each one is a complete, self-contained unit of business logic and its own data, not a tiny fragment. A monolith can also be horizontally scaled (multiple instances behind one entry point, sharing a database) — that's a common misconception the video corrects directly.

MonolithMicroservices
ProsSimple mental model; shared setup code written once; fast in-process calls; easy for small, cohesive teamsScale only the hot service; new hires learn one bounded service, not everything; parallel team development; clear per-component load visibility
ConsNew engineers must understand the whole system; every change redeploys everything; a single bug can take the whole system down (no partial failure)Genuinely hard to design well; risk of over-decomposing into "chatty" services that constantly call each other over the network
Real examplesStack Overflow (monolith success story)Google, Facebook
The "should these be separate?" test

If Service A is just talking to Service B constantly, that's a smell — it should probably be one function call inside a single service, not a network hop between two. Interview framing: microservices are "more often than not" the better default answer at scale, but you're expected to justify it with real trade-offs, not state it as a buzzword.

What Is Database Sharding?

Horizontal partitioning: splitting rows across multiple servers by a chosen key attribute — contrasted with vertical partitioning, which splits by columns instead. Analogy used directly: slicing a pizza and giving each friend one slice, so no one server has to serve the whole pie.

Sharding key
The attribute deciding which shard a row lives on — e.g. user ID, or city/location (Lyft's real-world example).
Consistency (as defined here)
"Whatever data you persist is what you can read out later" — read-your-writes correctness.
Hierarchical sharding
When one shard itself grows too large, it's split again into mini-slices under a manager/router layer.
The two core problems

Cross-shard joins: a query needing data from two different shards requires an expensive network round-trip between them. Inflexibility: naive (modulo-based) sharding forces a costly full remap whenever the shard count changes — solved the same way Video 4 solved it, with consistent hashing (Memcached cited as a real implementation).

Gaurav's parting recommendation: don't reach for sharding first — try indexing, or a NoSQL database, or an established managed sharding solution before building your own. Database servers are stateful (must persist reliably); application servers are stateless and trivially scalable — which is exactly why sharding a database is a harder problem than scaling app servers.

0811:25

Caching in Distributed Systems: A Friendly Introduction

Instagram feed example: the round trip is 220ms, but caching only ever touches the 20ms database leg — a deliberate caution against overestimating caching's real-world payoff.

Even at a realistic 90% cache hit rate, the video's own math works out to "less than 10%, maybe 2 or 4 milliseconds" of actual savings — a direct correction to the assumption that caching is automatically a huge win.

What's worth caching

Small in size, read frequently, changes rarely. Cache trashing: a fixed-size cache fed a strictly sequential, non-repeating access pattern (1, 2, 3, 4, 5…) causes constant eviction with zero benefit — pure wasted overhead.

Eviction policies
LRU (least recently used) and LFU (least frequently used) — the two every engineer should know.
Three cache tiers
In-memory/application (a plain Map), database-level (automatic, a "blackbox"), and distributed/global (its own server, shared across services via get/put).
Client-side caching
A mobile app storing the feed locally cuts repeated-scroll response time from 200ms to 2ms.
Staleness tolerance
YouTube like-counts update hourly — fine. Financial transactions — never acceptable.
096:34

How to Avoid a Single Point of Failure in Distributed Systems

One database everything depends on, versus a master with read slaves — redundancy at every converging point, not just one.

The math behind redundancy

If one node's failure probability is P, requiring two independent nodes to both fail drops the effective outage probability to P² — the core justification for why redundancy mathematically compounds in your favor.

The trap: fixing one SPOF can just relocate it — adding a load balancer to fix backend redundancy makes the load balancer itself the new SPOF, unless it's also made redundant (e.g. via DNS resolving to multiple IPs). Elimination has to run end-to-end: gateway/DNS → load balancers → app nodes → coordinator → database. Netflix's Chaos Monkey is cited as the real-world practice of randomly killing production nodes to continuously verify resilience.

105:43

What Is a CDN (Content Delivery Network)?

A CDN geographically distributes smaller copies of a centralized cache, so users hit a nearby edge node instead of round-tripping to one distant central server. It solves two separate problems: latency (no single location is close to everyone — Japan, the US, and India can't all be well-served by one server) and data localization (content legally restricted to one country can be kept only in that region's cache).

CDN node
An actual server — its own IP, file system, and API — not "dumb storage." An origin/master server populates and manages each node's files.
Regulatory example
Movies restricted to India can't be shown in the US or Japan, and vice versa for US-only content.
Named implementation
Amazon CloudFront — integrates with S3, auto-propagates to edges on upload. GCP and Azure offer equivalents.

Best suited for static content (video, images, files), not dynamic per-request computation. Research cited (Amazon/Google) links latency directly to users' perceived trust in a service — a half-second delay is enough to matter.

1111:25

What Is the Publisher Subscriber Model?

Replaces direct service-to-service request-response calls with a message broker (Kafka, RabbitMQ): a publisher fires and forgets, and subscribers consume independently — one failure point (the broker) instead of many cascading ones.

Why it's dangerous for money

Worked example: Account A starts at 1000 rupees. A commission service deducts 50 immediately on each transfer request, independent of whether the transfer itself succeeds. Two transfer requests (950, then 800) queue while the transfer service is down; commission deducts 50 twice (balance → 900); when the broker finally delivers both messages, the 950 transfer fails (insufficient funds) but the 800 succeeds. Final balance: 100 rupees, not the expected 0 — because commission deductions weren't atomic with the transfers they were tied to.

At-least-once delivery means the broker persists and retries a message until it's consumed — which makes idempotency (via request/transaction IDs) mandatory in every handler, or replays cause duplicate side effects (the video's second failure example: a 50-rupee withdrawal deducted twice because the message carried no ID to detect the duplicate).

Good fit: gaming analytics, Twitter-style broadcast fan-out. Bad fit: anything needing strict atomicity, like finance.

1214:59

What's an Event Driven System?

Services never call each other directly — a service publishes an event ("something changed") to an event bus, and subscribers independently consume and store it. The key extra capability over plain pub/sub: because every event is durably logged, you can replay history — rebuild a new service from scratch, or debug past state by walking the log to any point in time.

The Counter-Strike example

Player 1 fires at Player 2 while Player 2 is at position 9 on Player 1's screen — but due to network lag, the server has already moved Player 2 to position 10, and denies headshot credit. Fix: the server takes the shot's timestamp and replays events backward to that exact moment to correctly judge whether it was a headshot from what the shooter actually saw.

Service replacement example: a new "Service 5" replacing "Service 2" simply asks the event bus for all events from time 0 to now, replays them locally, and becomes consistent — a smooth swap instead of a hard cutover.

Where it breaks down

A service with external side effects (e.g. an email service) can't be safely replayed — an external system's response varies each time you replay, so naive full replay produces different real outcomes. Three approaches to historical state are named: full replay (impractical at scale), incremental/diff storage, and undo operations (works for reversible math, not for "an email was sent"). Program flow also becomes hard to trace — reading Service 1's code shows only that it published an event; you must separately inspect the bus's subscriber list to know what happens next.

Introduction to NoSQL Databases

Opens by knocking down a myth: scale alone doesn't imply NoSQL — YouTube, Stack Overflow, Instagram, and WhatsApp are all massive-scale systems that don't rely on it for primary data.

SQL vs. NoSQL storage model

A Person row in SQL uses a foreign key (e.g. Address ID 23) to a separate table. In NoSQL, the same person is one self-contained JSON blob with the address nested inline; missing fields simply aren't stored — no enforced schema.

NoSQL advantageWhy
Data localityRelated fields live in one block, matching write-everything / SELECT * access patterns; avoids joins.
Schema flexibilityAdding a field (e.g. salary) doesn't require rewriting/locking the whole table.
Built-in horizontal partitioningDesigned for scale-out from the ground up, trading consistency for availability.
NoSQL disadvantageWhy
No ACID guaranteePoor fit for financial/transactional systems.
Column-specific reads are inefficientGetting "all employee ages" means reading whole blobs and filtering row by row.
No referential integrity, manual joinsNothing guarantees a referenced ID exists; joins are done in application code.

Cassandra's distributed architecture

5-node consistent-hash ring; a bad (non-uniform) hash function was shown crashing one node with ~400 of 500 example requests — fixed with a second-level hash (Google Maps' real fix for local festival load spikes).

The quorum failure window

A profile write lands on node 5, replicating to nodes 1 and 2 — before that finishes, node 5 crashes, and a read hitting node 1 (still empty) wrongly reports "not found." Quorum=2 of replication factor 3 accepts this small false-negative risk for higher availability; quorum=3 requires all three to agree, so one downed node fails the whole read — the video explicitly frames this as "really rare" and an acceptable trade for availability.

Storage engine internals

Writes append to an in-memory table (no search needed, pure sequential write); once full it flushes to disk as a sorted, immutable SSTable (concept from Google's BigTable). Repeated updates to the same key create duplicate SSTable entries — compaction merges tables (like a merge sort, O(N) time) to deduplicate and reclaim space. Deletes write a tombstone marker rather than removing data immediately. These SSTable/compaction/tombstone mechanics are shared by Elasticsearch and DynamoDB, not unique to Cassandra.

1415:26

What Is an API and How Do You Design It?

An API is "a documented way in which external consumers can understand how they can interact with your code" — worked through a running WhatsApp-style "group admins" example.

  • Location/routing — which microservice owns this endpoint? Example: a Group Service owns group-related calls.
  • Naming must match behavior — a getAdmins that silently also returns memberships is mis-named; it becomes getAdminsAndGroups, or gets split in two.
  • Parameter minimalism — don't add parameters unless necessary; an exception for performance (avoiding 4-5 expensive inter-service calls) is fine, but then rename the function to reflect the wider scope.
  • Response minimalism — don't over-stuff responses "just in case" for future use; it bloats payload and confuses callers.
  • Error-handling responsibility — an API taking an integer groupID shouldn't also validate string-to-int conversion or a DB's string-length limits; split expected errors (group doesn't exist) from systemic ones.
    • Atomicity example: setAdmins

    A fat setAdmins(admins, groupID) that silently auto-creates the group or auto-adds missing members is "a really weird API" — if group-creation succeeds but setting admins fails, you're left with an adminless group another process might auto-fill, causing conflicts. Fix: split into explicit sequential calls — createGroup(members) then setAdmins(admins, groupID) — achieving atomicity through explicit ordering instead of one call silently doing several things.

    URL anatomy example: /v1/chat-messaging/getAdmins = domain → service → action → version (the version exists specifically so a future v2 can be non-breaking). Pagination (client-facing, offset-based, e.g. getGroupMembers for 200 members in batches of 10) is distinguished from fragmentation (internal server-to-server, numbered packets like TCP sequencing when a response exceeds a size cap).

    Consistency vs. performance: a concurrent getAdmins call might return 2 admins when a 3rd was just added — the guiding question is "do you really care?" (a comments API tolerating ~3 seconds of staleness is the example given as an acceptable trade for throughput).

    System Design: Tinder as a Microservice Architecture

    Design approach emphasized up front: work "front to back" — features → services → data — rather than starting from an ER diagram; "keep it fluffy" during requirements, and make the server the source of truth.

    Message send flow: Gateway validates auth → Matches Service confirms mutual match → Session Service looks up recipient's live connection.

    Files vs. DB blobs (image storage): a distributed file system wins over DB blobs for images — cheaper, built for large objects, faster retrieval, enables CDN use; the DB keeps only URLs/metadata.

    ServiceJob
    Profile Serviceregistration, auth, profile metadata (name, age, gender, location)
    Image Serviceseparate from profile; stores profile/image ID + URL into the distributed file system
    Gateway Servicesingle entry point; validates auth tokens; routes; decouples protocol handling
    Matches Servicebidirectional match records; source of truth for whether messaging is allowed
    Session Serviceuser ID → active connection/socket ID
    Recommendation Servicefilters candidates by location (refreshed every 1–3 hrs), age, gender
    The single-index problem, and the fix

    A relational DB can't efficiently serve location + age + gender together — the query optimizer only picks one index. Fixed either by NoSQL replicated query-pattern tables (Cassandra/DynamoDB) or by sharding by location and filtering age/gender in-memory afterward. ~1M active users assumed; match rate ≈ 0.1% of swipes (daily matches ≈ active users × 10⁻³). HTTP polling was rejected in favor of XMPP (peer-to-peer, server-push capable) for chat, over persistent WebSocket/TCP connections.

    1624:29

    Designing Instagram: System Design of News Feed

    Core decision: a naive live-query feed (join all followees' posts at request time) is rejected outright — "it's going to get bombarded... definitely not gonna scale." The fix is fan-out-on-write: pre-compute and cache each user's feed.

    Fan-out-on-write: a new post is pushed into every follower's pre-computed, cache-capped-at-20 feed — reads become a simple cache lookup, not a live join.

    The celebrity problem

    Push works fine for normal users but fan-out to millions of followers can crash the system for celebrity accounts. Hybrid resolution: push for normal users; for celebrities, either pull (followers poll ~every 10s) or batched push in chunks of 100–1,000 every ~10 seconds.

    Schema choices: a single generic Like table (like_id, user_id, parent_id, type = "post" or "comment") avoids separate like tables per entity type; a separate Activity table stores aggregated counts to avoid recomputing them from raw likes each time. Comments are single-level only (no nested replies) to bound complexity. Feed capped at top 20 posts per user. Load balancer routes via consistent hashing on user_id, snapshot refreshed every ~10 seconds. Cache (not DB) chosen for storing computed feeds specifically because it's recomputable if lost, and naturally favors recently-active users.

    1725:15

    WhatsApp System Design: Chat Messaging Systems for Interviews

    Scoped tightly to messaging — image/video sharing is explicitly punted to the Tinder video. Core requirement: 1-to-1 and group (capped at 200 users) messaging with sent/delivered/read receipts and last-seen status.

    Gateways are deliberately "dumb" (no parsing/auth) to keep per-connection memory low; a separate Parser/Unparser service does Thrift conversion downstream.

    ServiceJob

    1810:44

    How Netflix Onboards New Content: Video Processing at Scale

    A single uploaded master file must serve every device over every network speed — without live re-processing on each play request.

    Format × Resolution
    Total encoded variants needed = formats × resolutions (MP4/AVI × 480p/720p/…) — a combinatorial fan-out from one source.
    Scene-based chunking
    Fixed 3-minute chunks caused mid-action scene cuts; switched to ~4-second, scene-boundary-aligned chunks instead.
    Sparse vs. dense viewing
    Documentaries (users skip around) vs. action films (linear viewing) — drives whether the system prefetches ahead.
    Re-encoding trigger
    A file shrinking from 6GB → 1GB with a better codec is worth reprocessing the catalog for.

    Open Connect Boxes — Netflix's physical caching appliances inside ISP data centers — handle ~90% of total traffic, refreshed with new content at low-traffic hours (~4am), curated per region (explicit examples: India, Britain, US). Encoded video is stored in S3, "extremely cheap compared to a database." YouTube uses similar edge appliances.

    1913:12

    Capacity Planning and Estimation: How Much Data Does YouTube Store Daily?

    The classic back-of-envelope skill: turn a vague scale question into concrete infrastructure counts via explicit, defensible assumptions.

    The full funnel: 10M min/day uploads → 30TB/day raw → 1TB thumbnail cache → 64 baseline nodes → ×2 for 50% utilization headroom → ×3 for geographic replication ≈ 500 nodes.

    The math, worked in full

    • Ingestion: 10,000,000 min/day × 3MB/min = 30TB/day raw video.
    • Thumbnails: 1MB original compressed to 10KB (100× reduction); caching 90 days × ~90M popular videos → 900GB ≈ 1TB cache.
    • Nodes: 1TB ÷ 16GB/node = 64 baseline nodes → run at 50% utilization (never 100%) → 128 nodes → ×3 regions ≈ ~500 cache nodes.
    • Processing throughput: system must sustain 400MB/sec; per-MB cost = read 10ms + process 20ms + write 20ms = 50ms → 400MB/sec × 50ms = 20 "seconds of work" needed per second of wall-clock time, i.e. 20× parallelism.
    • At 20MB/sec per processor: 400 ÷ 20 = 20 processors minimum — before any safety margin is applied.
    The one rule that matters more than the arithmetic

    Redundancy and headroom are non-negotiable: sizing to the exact computed minimum (64 nodes at 100% utilization, exactly 20 processors) is fragile. Compute the raw numbers first, then apply real-world multipliers (safety margin, replication) — reversing that order under-provisions the system.

    How Databases Scale Writes: The Power of the Log

    Fast writes come from borrowing a linked list's append-only philosophy (O(1) writes); fast reads get clawed back afterward by periodically re-sorting and merging that log — this combination is the Log-Structured Merge (LSM) Tree.

    The full lifecycle: in-memory log fills → flushes to an immutable sorted SSTable → multiple SSTables accumulate → background compaction merges them into progressively larger sorted levels → bloom filters let a read skip tables that definitely don't contain the key.

    ScenarioSearch cost
    3 chunks of 6, unmerged3 ops × 3 chunks = 9 operations
    Merged into 1 chunk of 18merge (~4) + search (~3) = 7 operations
    4 chunks of 6, unmerged3 ops × 4 chunks = 12 operations
    Fully merged into 1 chunk of 24log₂(24) ≈ 5 operations

    Bloom filter (analogy: 26 boolean slots for A–Z, checking if the word "cat" could exist): false positives are possible (the filter says "C" exists because of "Katrina," not "cat"), but false negatives are impossible — if a letter is unmarked, no word starting with it exists. That guarantee is exactly why it's always safe to use as a skip-filter.

    2115:48

    Distributed Consensus and Data Replication Strategies on the Server

    The progression: single DB (SPOF) → replicated DB → the split-brain problem multi-master replication creates → consensus protocols that resolve it.

    The video's central cautionary example: a 120-rupee account hit with two independent withdrawals (100 + 50) on either side of a network partition — each master only sees its own local balance and approves, driving the true balance negative.

    Async replication
    Replica updated after the fact — less load, but staleness risk.
    Sync replication
    Master sends the actual update commands via a transaction log; the slave replays them in the same order for identical state.
    Master-master
    Both nodes accept writes — better availability, but this is exactly what enables split-brain.
    Odd-node quorum
    A third node (C) arbitrates when A and B diverge (S0,S0,S0 → SX vs. SY), forcing rollback/resync until agreement.

    2PC is called "popular but really slow"; 3PC is named as an alternative. MVCC (used by PostgreSQL) sidesteps a single global choice by keeping multiple row versions — allowing either a fast dirty read of an older version or a strict serializable read. The Saga pattern avoids long lock-held transactions by breaking them into local steps with compensating rollbacks — examples given: reserving 200 rupees pending order confirmation, and billing a phone call in committed 1-minute increments rather than one giant end-of-call charge.

    2222:22

    Designing a Location Database: QuadTrees and Hilbert Curves

    How to answer "find things near this location" fast. Naive encodings (pin codes) group locations administratively, not geometrically — two pin codes 400051 and 400050 can be ~2km apart across a rail line despite looking "adjacent."

    QuadTree: a 20-point region splits top-right(5)/top-left(3)/bottom-left(1)/bottom-right(11) — the overpopulated bottom-right quadrant (11 > a 10-point threshold) splits again.

    Hilbert curves convert 2D position into a single 1D ordering (a "space-filling curve"), which lets proximity search become a cheap 1D range query — but the conversion is lossy. Worked example: a query for position 29 ± 6 covers curve-range 23–34, but point 18 (2D-close to 29) sits 11 away on the curve — a false negative; widening the threshold to catch it then pulls in point 40, which is curve-adjacent but 2D-far — a false positive. Chosen over the simpler Z-curve specifically because it preserves locality better (fewer long jumps).

    2325:42

    Data Consistency and Tradeoffs in Distributed Systems

    Uses an early-Facebook-at-Harvard analogy (single server, campus-only) to motivate replication, then walks the mechanics of Two-Phase Commit (2PC) as one concrete answer to keeping replicated copies consistent — and its direct cost to availability.

    2PC's prepare → ack → commit sequence — strong consistency, at the direct cost of the system being locked/unavailable during the coordination window.

    Four explicit failure scenarios walked through: (1) prepare fails → rollback; (2) prepare succeeds but the commit message is lost → timeout-triggered rollback, retried via transaction ID; (3) commit succeeds at a follower but its ack is lost → leader safely retries (idempotent, tracked by transaction ID); (4) commit succeeds at the leader but fails at some followers → reads/writes stay locked until resolved. Timeout window example: 5–6 minutes before an un-committed prepare auto-rolls-back.

    The stated bottom line

    "If you have pure consistency, your system is not available; if you have availability, your system will suffer inconsistencies." 2PC fits financial systems (where consistency must be total) but is a poor fit for something like a social feed. Eventual consistency is flagged as the alternative, deferred to a follow-up video.

    System Design Interview: TikTok Architecture (with @sudoCODE)

    A live mock interview (Gaurav Sen interviewing Yogita Sharma) designing a TikTok/Reels-style platform — requirements → capacity estimation → storage architecture → processing pipeline → CDN strategy.

    Upload returns HTTP 202 immediately; a queue absorbs spikes while chunking (10s pieces) and parallel transcoding happen asynchronously before landing in S3 and replicating to 4 regions.

    Capacity math walked in the interview

    • DAU derivation: 1B total downloads ÷ 100 = 10M daily viewers; 10% of those (1M) are "power users."
    • ~100,000 creators; write:read ratio ≈ 1:100 (heavily read-heavy).
    • Uploads: conservative 1 video/creator/day = 100,000 files/day; realistic 5/day = 500,000 files/day.
    • Storage: 200,000 videos × 1MB = 200GB → ×2 for 4 formats ≈ 400GB → ×2 for resolutions ≈ ~1.2TB/day total.
    • Fan-out per original video: 4 formats × 200 device types × 3 resolutions ≈ 2,400 derived files per upload.

    5 Tips for System Design Interviews

  • Don't go into detail prematurely. Diving deep on one component before the interviewer has seen the full architecture wastes time and risks backtracking. State intent at a high level and pause for feedback before elaborating.
  • Don't walk in with a fixed architecture. Don't force the problem into a pattern you personally favor (e.g. always reaching for pub-sub). Interviewers deliberately introduce new requirements mid-interview to test adaptability — stay flexible.
  • Keep it simple — avoid tunnel vision. Don't over-elaborate one part (heartbeats, analytics DBs) while leaving the rest thin. Periodically zoom out; if one section of the diagram looks huge and another tiny, rebalance.
  • Always justify technology choices. Never state a choice ("the database will be Cassandra") without saying why — an unjustified assertion is a negative signal, not a positive one.
  • Know real, current technologies and name them specifically. Say "Cassandra" or "DynamoDB," not "a NoSQL database." Naming real tools (an elastic load balancer, Zookeeper, RabbitMQ) signals you know what would actually make the system work.
