Frontend System Design, Explained

Structured notes on the frontend-specific counterpart to backend system design — microfrontends, monorepos, MCP UI, and the rendering/performance layer — including where AI coding agents change the calculus.

Title: "Frontend System Design Explained w/ Senior Engineer" Channel: theSeniorDev Video ID: KuClyhvSzXk

01

Why Frontend System Design Matters Now

The framing premise: as AI coding agents get better at raw implementation, the thing that differentiates a strong frontend engineer stops being typing speed and starts being architecture and system design — a skill set most "system design" content ignores entirely in favor of backend-only material.

The core strategic shift stated in the video

Coding agents cut implementation time but increase verification time — someone still has to check the agent's work. The design goal becomes building systems that "decrease verification time and minimize architectural drift while maximizing velocity." It's "not anymore about implementing fast but rather building a system that is extremely easy to verify."

02

Microservices, Briefly

Set up as the backend precedent frontend architecture mirrors: breaking a monolithic backend into independent small backends, each exposing an API, typically layered as API layer → business logic layer → persistence layer → database (Postgres, or a NoSQL store). Each microservice deploys independently, on its own codebase, and services only talk to each other through APIs.

Conway's Law is the stated reasoning for why this matters at all: "the soft architecture of a system will look like the organization of the people" — so enabling independent teams requires structuring the code into independent vertical slices, not the other way around. Two-pizza teams (Jeff Bezos' principle: 5–9 people) is cited as the target team size, with an explicit aside that AI shrinks it further — "one pizza team becomes smaller with AI."

03

Microfrontends

The problem: splitting the backend into microservices doesn't help if the frontend stays a single monolith — "so many people pushing code to the same client that it's so easy for someone to make a mistake or bring the whole system down," plus the coordination overhead of everyone touching one codebase.

A shell owns global concerns and dynamically loads independent frontend apps — each a separately deployable domain. The video's example: Amazon likely splits header, product page, and payment into microfrontends "with even more granularity" than this.

Vertical slicing: each feature is owned end-to-end by one team, and one microfrontend typically talks to one or a few microservices in the same domain — so "releases are not a bottleneck for another team."

04

Two Career Paths This Creates

Path 1 — feature team
Works a vertical slice full-stack: "a team of one that can work with the coding agent across the full stack."
Path 2 — infrastructure
Builds the shell, owns the design system, or works on the platform team.

Direct claim: "if you are an engineer and you're doing only front end or back end, you have to move as fast as you can towards becoming a vertically integrated engineer."

Why microfrontends specifically help with AI coding: they decrease the blast radius of a production bug, reduce cognitive load via smaller, localized PRs, and — directly — give the coding agent less context to hold, making it more efficient and the change easier to verify.

Talking to the backend

topics 5 – 9

05

API Gateway

Problem: multiple microfrontends each hitting multiple backend services means re-implementing caching, HTTPS, auth, content negotiation, and rate limiting redundantly, on both client and each backend service.

Fix: a single gateway sitting in front of every backend service. The client implements these "edge" concerns once; individual services never duplicate the logic. Backend services then live inside a private network (a VPC), reachable only through the gateway.

A performance detail worth keeping

Client-to-gateway traffic uses HTTPS; gateway-to-microservice traffic inside the closed network can use plain HTTP — skipping the extra round trips of a TLS handshake where the network is already trusted. Recommendation: "once you have a couple of microservices in production it's a good idea to add an API gateway both for security and performance and also less complexity in the front end."

06

Backend for Frontend (BFF)

Problem: a frontend calling several microservices directly means juggling several different API shapes and needing a different client SDK per service — and any feature needing even a slight backend change means going to talk to that backend team, waiting for it to become their priority. The video notes this is a real, named frustration even for senior engineers at large companies who "have to talk to three different backend teams" just to ship a feature.

Each client gets its own dedicated backend, owned by the frontend team, sitting between it and the "pure" microservices owned by backend teams.

Why per-client, not one shared API: desktop wants to fetch a lot of data at once; mobile's smaller screen needs fewer, smaller records. A single unified API "risks being bloated, or it will end up not satisfying one of the requests" — the classic over-fetching (desktop payload wasted on mobile) / under-fetching (mobile-sized responses forcing desktop into many requests) trade-off. "It's a lot better if you split those things."

GraphQL is named specifically as "a great technology to build backends for frontends," and the video calls it "a requirement for all the front-end engineers that you see working at bigger companies." Building a BFF means the frontend team needs to know API design, GraphQL, and at least the high-level shape of extending a microservice.

07

Load Balancing

A "typical Node.js server is pretty powerful — you can usually satisfy up to 2,000 to 10,000 concurrent requests." Beyond that, identical server instances are spun up and an application load balancer splits traffic between them.

How deep a frontend engineer actually needs to go

"You don't need to go so deep into it, but do make sure you know about it." The video suggests being able to set up a small load balancer with Nginx + Docker Compose as a learning exercise, while noting most cloud providers (AWS, GCP) provision one "in seconds" — "it's very uncommon that you need to manually set up one, but it's important that you know about it."

08

Docker & Kubernetes

Problem: a distributed system spans different technologies (Python microservices, Node.js services, Vue/Next apps), each with a different build and deployment process.

Docker packages an application into an image via a Dockerfile "recipe" — app code, runtime (e.g. Node.js for a Next.js app), and OS (typically Linux) all bundled together. "Wherever you find a host that runs Docker, you can run that image" — no separately installing the right Node version, PHP, or dependencies.

Container orchestration (Kubernetes, AWS ECS) then manages the deployment pipeline, runs multiple instances, restarts containers on failure, and load-balances between them.

The expectation, stated directly

"Do you need to know Kubernetes as a front end engineer? No. You do need to know about it. And you will see a lot of front-end positions that mention either Kubernetes or container systems or ECS." Framed reassuringly: "don't be scared, you don't need to become a DevOps engineer by tomorrow, but you should be able to at a high level understand where it fits in your architecture."

09

CDN

The physics problem: a US user hitting a Europe-based app pays a real, unavoidable latency cost — "there's no physical way you can work around it... there is the limit of the speed of light." Estimated cost: 200–250 milliseconds added per request.

Fix: a network of edge locations distributed globally; the origin server pushes static assets to them, and a user's request gets redirected to the geographically closest edge — a cache hit in the video's own terminology. Cache invalidation is the flip side: the server pushes a new version, but old copies can linger at edges, which is why module bundlers use cache-busting to guarantee users get the latest version on deploy.

Called out as going beyond simple placement: modern CDNs also handle compression and cache-policy management — "the fastest and most cost-effective way to increase web performance... out of the box."

topics 10 – 13

10

Design Systems

Problem: independent feature teams releasing independently drift visually — "a button in the product page will look differently than a button on the payment page," and users start to notice the app is really several separate frontends stitched together, on top of the wasted, repeated code.

Layer 1 — design tokens
Primary color, border definitions, font families — implemented as CSS custom properties (global variables) typically in the shell microfrontend, then fed into every other microfrontend.
Layer 2 — component library
Shared inputs, buttons, etc., consumed as a UI package across every microfrontend — consistency and zero repetition, "the DRY principle applied at the architecture level."
Baked in
Accessibility and unit testing live inside the design system itself, not re-solved per feature team.
Why this matters even more with AI coding

Without a design system, an agent generating a component "will make things up and your UI would just look different — it will be obvious that it was vibe coded." With one, the video's own practice is stated directly: "the first thing I do whenever I get a new project is try to extract from whatever the design is the design system" — then feed it into the coding agent across sessions for consistent, reliable output.

11

Design-to-Code MCP

An MCP (Model Context Protocol) server here is described as "the glue layer between design tools and coding agents" — instead of designers building in Figma and engineers manually re-implementing it in code, a Figma MCP server plugs directly into the coding agent for rapid assembly of a feature into a vertical slice. The video frames this as the direction "most companies are moving towards."

Skill expectation: know what MCP servers are, know your design tool's MCP capabilities, and ideally be able to plug one in yourself — or build the connection if it doesn't exist yet. Claude Code is named as the most-used coding agent in enterprise, with Codex mentioned as an alternative.

12

Atomic CSS & Tailwind

The execution layer for design tokens: define a property (e.g. a border style) once, then generate an atomic class (.border) from it. Tailwind CSS is described specifically as "an implementation of the atomic CSS architecture style for CSS" — one of (per the video) four architectural styles for CSS in total, with the other three left for a possible future video. In practice, developers only reach for the pre-defined atomic classes instead of writing bespoke CSS per component.

13

Monorepo

Problem with many separate repos ("thousands of repos" at scale): different code styles, different dependency versions, inconsistent TypeScript adoption, inconsistent lint configs — architectural drift, where projects diverge too far from a shared standard. A real cost named directly: "if you're a developer and you change teams, you have to relearn everything."

Fix: one repository holding every application, with tooling that operates across all of them at once — npm run build in a monorepo builds every application individually, from one command.

Why this specifically matters for AI coding

"A monorepo gives coding agents the context they need to make changes across service boundaries." Worked example: while building a microfrontend, the agent notices a reusable pattern and extracts it straight into a shared design-system component — in one session. Without a monorepo, "you have to somehow feed those two different repositories to your coding engines and everything becomes harder." Direct recommendation: combining microfrontends + microservices with a monorepo is "usually the most efficient way to work with AI."

14

MCP UI

Framed as the hybrid of a traditional website and an LLM-powered chat app — "the glue in between them, the duct tape, let's say that." Traditional chat UI: send a query, get text back. MCP UI's addition: the LLM's answer can also render actual UI components, not just text.

Worked example from the video

Searching for event venues for an annual in-person meetup across European (and possibly US) locations — the chat interface renders venue results, lets you keep drilling in conversationally, and generates maps, all inside one chat application.

Mechanically: the model harness provides the registries and MCP servers in context; the LLM sends back both a text answer and an instruction to render a specific component ("div"); the frontend parses that instruction from the LLM's response and renders it. An MCP resource is declared to the LLM ("there's this resource, use it in this scenario, this is the answer you can give"), and the frontend has to parse and render whatever comes back.

The video's actual take on "chat replaces UI"

Direct pushback on a common narrative: "a lot of people were saying that there's no more need for a UI now that we have a chat. I disagree... the UI is a very useful way to communicate things." The predicted future is a hybrid — not chat replacing frontend engineers, but frontend engineers combining the LLM approach with traditional web UI, especially for specific edge cases the video says "goes way beyond the current AI hype."

Core Web Vitals

Three metrics, measured and benchmarked by Google, each covering a different performance dimension — called out as "the most important pattern that you'll even see now mentioned in job descriptions for front-end engineers."

MetricDimensionMeasures
LCP — Largest Contentful PaintLoading speedTime from entering the URL to the largest page element rendering
INP — Interaction to Next PaintInteractivity speedTime from a user interaction to the UI repainting — relevant to how component frameworks re-render
CLS — Cumulative Layout ShiftVisual stabilityHow much the UI shifts around while the page loads

The critical rendering path: HTML → DOM → CSSOM → render tree → layout (node positions/widths) → paint operations sent to the GPU → composite.

What drives each metric: LCP suffers from too much JS, too much CSS, heavy data fetching, or a slow server. CLS comes from CSS/fonts/data loading asynchronously and shifting content — the browser literally screenshots the page to measure how much it moved. INP suffers from slow renders or excessive re-rendering when a user interacts. LCP and CLS are about the initial render; INP is about re-renders.

16

Code Splitting & Lazy Loading

A bundler that puts all JavaScript into one file "will totally mess our core web vitals because we load too much JavaScript" up front. Code splitting ships only what a specific page needs — a /login page gets login-only code; a chart-heavy dashboard doesn't burden every other page with that weight. Webpack and Vite handle this by understanding the bundle, splitting it, and dynamically loading pieces in coordination with the app's router.

Eager vs. lazy: eager loading fetches everything the moment the page lands; lazy loading defers until it's actually needed — on scroll, on visiting a specific page, on click, on some other interaction. The goal throughout: "on the page you really only ship the things they need."

17

Rendering Strategies

The starting problem for every component framework (React, Vue, Angular): a "white screen of death" — HTML loads, but nothing appears until the framework's render function actually executes.

StrategyHow it worksFit
CSR — Client-Side RenderingGet static HTML → fetch dynamic data → render in the browserSPAs; weak for performance-critical sites and SEO, since crawlers can't see content until JS executes
Static pre-renderingFully rendered on the server ahead of time; client gets ready HTML+CSSStatic sites with little interactivity only
ISG — Incremental Static GenerationOnly regenerates the pages that changed (e.g. a CMS triggers a rebuild on a new blog post)Content that changes sometimes, not every request — "built into a framework like Next.js, so you never have to worry about this yourself"
SSR — Server-Side RenderingClient requests the frontend server → it requests the backend for data → renders the app on the server → sends pre-rendered HTML, then hydrates (builds the virtual DOM and attaches it to the pre-built markup)Genuinely fast performance + SEO needs only
The strongest opinion in the whole video

SSR is "one of the most complex approaches" — "be careful with it." Direct criticism of overuse: "a lot of people in a lot of companies jumped into this and they're doing server-side rendering, but that's like building an F1 car to go do the groceries. It's overengineering, and it creates a lot of problems, and then everything is slower." Recommendation: default to simpler solutions "unless your use case really needs the highest performance."

18

Real-Time Data Fetching

Framed as part of the "vertically integrated" frontend engineer's job — plain request-response doesn't cover every case, especially ones needing ongoing updates.

ApproachMechanismTrade-off
PollingKeep calling an endpoint until an event occurs (e.g. poll a transaction-status endpoint until "completed"); trivial with setTimeoutSimple, but over-calls the server, scales poorly, and risks race conditions — "very simple, but not the most performant"
WebSocketsOpen bidirectional channel; both sides send messages freely (e.g. a chat app)Real overhead, complex to implement, resource-intensive on the server — "for most use cases this is not really needed"
SSE — Server-Sent EventsClient sends one message; server streams updates back over that connection — inherently asymmetricThe natural fit for AI chat: "you send a query and then just wait... the server is sending a lot of messages but you usually only send one"
Where this shows up in practice

Named directly as what powers most LLM applications' token streaming — the OpenAI npm package uses this under the hood. Observable in the browser: open the network tab in ChatGPT or Claude, find the conversation request, and see the event stream delivering chunks of the answer as they arrive — "that's how you build these cool UIs" for streamed responses. Explicitly not WebSockets and not polling.
