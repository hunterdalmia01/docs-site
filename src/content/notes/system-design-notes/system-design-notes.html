System Design Field Notes

A structured walkthrough of how a single $10/month server for a photo-sharing app grows, failure by failure, into a load-balanced, cached, replicated, and sharded system — the reasoning at each step, not just the vocabulary.

Source: "System Design for Beginners (2026)" Channel: KodeKloud Video ID: SE2KF-vxvS0

01

What system design actually is

System design is the skill of choosing the right components and putting them in the right place to solve a software problem. It's not about memorizing a list of tools (Redis, Kafka, sharding) — it's about knowing which of those tools a given problem actually needs, and why.

The video frames it as a career-progression skill:

Junior engineer
Builds a specific feature with known inputs and outputs.
Mid / senior engineer
Figures out the approach and how it fits the rest of the system.
Senior / staff engineer
Designs the architecture the whole system will run on.

Throughout, the video uses one running example — a photo-sharing app — and evolves its architecture one failure at a time, so every component gets introduced as the answer to a concrete problem rather than a buzzword to memorize.

02

Functional vs. non-functional requirements

Functional requirements describe what the app does — sign up, upload a photo, follow a user, scroll a feed, like, comment. They either work or they don't, and you can see them in a demo.

Non-functional requirements describe the quality of how it does it — speed, durability, scale, availability, cost. They're invisible in a demo, but users feel them immediately.

Key insight

Two apps can share identical functional requirements — Instagram and a private family photo app both "let you upload and view photos" — and still be completely different systems, because their non-functional requirements (scale, availability, cost tolerance) diverge wildly. Almost every component that gets added later in this doc exists purely to satisfy a non-functional requirement.

Five questions to ask before designing anything

The video's recommended opening move — in an interview or in real work — is to spend the first few minutes asking questions, not drawing boxes.

QuestionWhy it mattersPhoto app answer
How many users, growing how fast?Determines whether you design for thousands or millions.10,000 today, doubling every few months → design for millions.
Read-heavy or write-heavy?Tells you where to spend optimization effort.Users scroll hundreds of photos a month but post 2–5 → heavily read-heavy. Optimize the feed path; uploads can be a little slower.

04

High-level design vs. low-level design

A recurring interview failure mode is answering at the wrong "altitude." Knowing which one you're being asked for — and saying so out loud — is itself a skill.

High-level design (HLD)
The zoomed-out blueprint: app servers, databases, caches, queues, CDN, and how requests flow between them. E.g. "Design Instagram."
Low-level design (LLD)
Zoomed into one feature: function names, data structures, class layout. E.g. "Design the like feature" or "Design an in-memory cache."
Interview move

State your altitude up front: "I'll stay at a high level — components, data flow, and trade-offs" — so you're not penalized for skipping code, or for droning on about servers when asked to design a single cache class.

Vertical vs. horizontal scaling

Vertical scalingHorizontal scaling
What it meansMake the one server bigger — more CPU, RAM, faster disk.Add more servers of modest size.
Code changesNone needed.Needs a load balancer and often a stateless design.
Cost curveNon-linear — bigger machines cost disproportionately more.Roughly linear — ten cheap machines vs. one giant one.
CeilingHard limit: the largest machine money can buy.No real upper limit — add an 11th machine anytime.
Failure riskStill a single point of failure.Failure of one machine doesn't take down the system.

Rule of thumb from the video: start vertical (it's simpler, no architecture changes), and shift to horizontal once you hit its ceiling or need to eliminate the single point of failure.

06

Stage 1 — one server does everything

The photo app starts on a single ~$10/month server that holds the web app, the database, and the uploaded photo files all in one place.

Simple, cheap, easy to test — and a single point of failure. This is the correct starting point for most new apps.

07

Stage 2 — three failures show up at 10,000 users

Growth to 10,000 users exposes three distinct, independent failure modes on that one server. Each gets its own fix — this is the mechanism the whole rest of the video repeats.

Failure 1 — CPU / RAM overload

Page load time creeps from 200ms to 10 seconds as one machine tries to serve everyone. Fix: add a second server (the first step into horizontal scaling) — which immediately raises a new question: which server should handle each incoming request?

Failure 2 — database overload

The same trending photos get queried over and over by millions of users hitting the database directly. Fix: introduce a cache (Redis) in front of the database — reads that used to take 20–30ms now return in about 1ms.

Failure 3 — single point of failure

A disk failure, a blown power supply, or someone unplugging the wrong cable takes the whole app down. Fix: replicate the database onto separate machines, and move photo files off the app server entirely into external object storage (e.g. S3).

08

Load balancing

A load balancer is not special hardware — just another server running load-balancing software, sitting in front of the app servers and deciding which one handles each request.

Request flow

  1. User types photoapp.com
  2. DNS lookup returns the load balancer's IP address — never an app server's IP directly
  3. The load balancer picks a healthy app server
  4. That server queries the database and returns the response

Load balancer = "reverse proxy." Health checks ping each server every few seconds; unresponsive servers stop receiving traffic.

Routing algorithms

Round-robin
1st request → server 1, 2nd → server 2, 3rd → server 3, then wraps around.
Least connections
Send the request to whichever server is currently handling the fewest active requests.
Weighted distribution
Account for servers of different sizes — bigger servers get proportionally more traffic.

09

Stateless vs. stateful servers

The bug

A user logs in and their session gets stored in server 1's memory. Their next request gets load-balanced to server 5, which has never heard of them — and they get logged out. The server was stateful: it kept important information in its own local memory.

Fix: make servers stateless. Strip all important data out of individual servers and put it somewhere shared — login sessions move into a shared Redis store that every server can read. Servers become disposable: you can add or remove them freely without affecting any user.

Not the same as stateful
Storing photo files in external object storage (S3) does not make a server stateful — the data was never local to begin with.
The tempting wrong fix
"Sticky sessions" (always route a user to the same server) just recreates the original single-server problem and defeats load distribution.

Data modeling — start from access patterns

Before choosing a database, list the questions the app actually needs to answer:

  • Show me a user's profile
  • Show all photos by a user
  • Show my home feed
  • Upload a photo
  • Like a photo
  • Comment on a photo
  • Follow another user

Those questions define the entities:

EntityFields
Usersid, name, email
Photosid, posted_by (user id), caption, upload_time, image_link (not the image itself)
Likesuser_id, photo_id, timestamp
Commentsuser_id, photo_id, comment_text, timestamp
Followsfollower_id, followed_user_id

Principle: every relationship is modeled as a pair of IDs plus the minimum extra information needed.

SQL vs. NoSQL

SQL (e.g. PostgreSQL)NoSQL (e.g. MongoDB)
Used forCore data: users, photos, likes, comments, followsSecondary data: preferences, behavior tracking, theme settings
WhyStructured, same fields every row; heavy relationships between entities; ACID transactions keep it consistent; joins power feed generation.Unstructured / flexible — records don't need matching shape.

In real production systems, it's normal for one application to use both databases, routing each write or read to whichever store fits the shape of that data.

12

Indexing

As the user base grows, queries slow down because the database is scanning every row linearly to find matches.

Fix: create an index on columns that are searched often — e.g. posted_by (fast lookup of a user's photos) and upload_time (fast chronological sort). An index works like a book's index: it points straight to the relevant rows instead of scanning the whole table.

Trade-off

Every index adds work to each write (insert/update/delete), since the index itself has to be maintained. Best practice: find your actually-slow queries first, then index the columns behind them — typically 3–5 indexes per table, not one on everything.

Caching and cache invalidation

What makes something worth caching

  • Small in size
  • Read frequently
  • Changes rarely

Examples from the app: trending photos, popular profile cards (username, picture, bio), and login sessions (read on every single request).

Cache hit: Redis answers directly, database untouched. Cache miss: query the database, then populate the cache for next time.

Keeping the cache honest

StrategyHow it worksWatch out for
TTL (time-to-live)"Lazy" approach — entry auto-expires after N seconds, next request pulls fresh data.Cache stampede: if a hot entry expires and many requests miss at once, they all hammer the database simultaneously. Defense: stagger TTLs so hot entries don't all expire together.
Active invalidationThe moment underlying data changes, immediately delete the cache entry so the next read misses and re-fetches fresh data.Requires remembering to invalidate on every write path — easy to miss one.

~30s TTL
Profile cards
A few minutes TTL
Trending lists
~60s TTL

14

Database replication

Three-copy architecture: one primary handles every write; two replicas answer reads only. The load balancer spreads read traffic across all three.

Replicas never accept writes directly — two independently-writable copies would conflict (e.g. X=9 on one, X=13 on the other).

Replication lag

Copying data from primary to replicas takes a few milliseconds, which makes replicas eventually consistent, not immediately consistent. Real bug: a user uploads a photo (written to primary), instantly refreshes their profile (read from a replica that hasn't caught up yet) — and the new photo appears to be missing.

Fix: route a user's reads of their own just-written data to the primary; other users' reads can safely use replicas.

Failover: if the primary dies, a replica gets promoted to be the new primary and the system stays online.

Replication ≠ backup

Replicas blindly copy everything — including mistakes. Delete data on the primary and that delete cascades to every replica. Real backups (point-in-time snapshots you can restore from) are a separate concern.

15

Database sharding

Eventually the data itself — billions of photos — no longer fits on one machine, no matter how many read replicas you have. Sharding splits the data itself across multiple database machines, so no single database holds everything.

Shard key: user ID. The routing formula sends each user's data to exactly one shard.

ProblemWhat happensFix
Hot shardsA celebrity account (huge read/write volume) happens to land on the same shard as another celebrity — that shard gets crushed while others sit idle.Choose a better shard key / rebalance manually.
Resharding nightmareAdding a 5th shard changes the formula from % 4 to % 5 — user 10 was remainder 2 (Shard 2), now remainder 0 (Shard 0). Almost all data has to physically move.Consistent hashing: each shard owns a small range of the ID space; a new shard only takes a slice from one neighbor, so only those users move.

MongoDB has sharding built in natively.

16

Monolith vs. microservices

MonolithMicroservices
StructureOne codebase, one deployment, all features (signup, upload, feed, likes) in one program.Separate services — upload, feed, notifications, likes — each independently deployed.
UpsideSimple, fast (direct function calls), one thing to test and debug.Independent scaling (feed gets 10 servers, upload gets 2), teams work independently.
DownsideCan't scale one piece independently of the rest.Network calls between services add latency and failure risk; one user request touching 5 services makes debugging much harder; needs a bigger team to run well.
Cautionary example

A 5-person startup ran 30 microservices and ended up spending more time debugging the network between them than building the product. Recommendation: start as a monolith (right choice for the photo app at 10,000 users); most real companies run a monolith plus a handful of extracted services — not hundreds of microservices.

17

HTTP, HTTPS, latency & bandwidth

Request flow

  1. DNS lookup: "Where is photoapp.com?" → returns an IP address
  2. HTTPS handshake: establishes a secure, encrypted channel
  3. Client sends the request, server sends the response

HTTPS = HTTP + encryption. Over plain HTTP, anyone on the network can read the data as plain text; over HTTPS, it's scrambled in transit.

Latency
Round-trip time for a single request.
Bandwidth
How much data can flow at once — the "width of the pipe."
Worked example

A feed that loads slowly is usually a latency problem, not a bandwidth one — e.g. fetching 30 thumbnails one request at a time means 30 separate round trips, each paying the latency cost, even though the total data size is small.

The final integrated architecture

Every box on this diagram exists because a specific failure, at a specific scale, demanded it — not because it's a "best practice" to include by default.
