01

Architecture & request lifecycle

A CRUD REST API sits between clients and a relational store, translating HTTP verbs onto rows. The shape that scales past a weekend project separates five concerns: routing (which URL/verb maps to which handler), validation (is the payload well-formed before touching the DB), controller logic (orchestration), data access (SQL / query builder), and error handling (one place that turns any thrown error into a consistent HTTP response).

Client │ HTTP request (JSON) ▼ Express app.js │ global middleware: helmet, cors, json parser, morgan logger ▼ Router ──────────────► /api/users (userRoutes.js) │ ▼ Validation middleware (Joi schema.validate(req.body)) │ 400 Bad Request if invalid ──────► errorHandler ▼ Controller (userController.js) │ calls service / model layer ▼ Data access layer (pg Pool.query with parameterized SQL) │ ▼ PostgreSQL (running in its own Docker container) │ ▼ Controller formats response envelope ──► res.json({ success, data }) │ ▼ (any thrown/rejected error at any layer) Centralized error-handling middleware ──► res.json({ success:false, error })

The point of this layering isn't ceremony — it's that each concern becomes independently testable and swappable. You can replace Joi with Zod, or raw pg with Prisma, without touching routing or error handling.

Why Docker hereDocker doesn't change the architecture above — it changes how consistently that architecture reproduces on every machine. Postgres in a container means "works on my machine" stops being a version-mismatch problem.

The services layer is what keeps controllers thin: a controller parses req, calls a service function, and shapes the response — it never writes SQL directly. That's the seam you'd cut along if you later swapped Postgres for something else, or added a cache in front of reads.

03

Docker & Docker Compose

Two containers: one for the API, one for Postgres, joined by a Compose network and a named volume so data survives restarts.

Dockerfile
FROM node:20-alpine AS base
WORKDIR /usr/src/app

# install deps in their own layer so `npm ci` is cached
# whenever only source files change, not package.json
COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "src/server.js"]
docker-compose.yml
version: "3.9"

services:
  api:
    build: .
    ports:
      - "3000:3000"
    env_file: .env
    environment:
      DB_HOST: db          # service name = DNS hostname on the compose network
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./src:/usr/src/app/src   # bind mount for live-reload in dev
    command: npm run dev

  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: apppass
      POSTGRES_DB: appdb
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  pgdata:
Why depends_on + healthcheck togetherdepends_on alone only waits for the container to start, not for Postgres to be ready for connections. Pairing it with condition: service_healthy makes the API container wait for pg_isready to succeed — this is the single most common cause of "connection refused" on first boot.

Files dropped into /docker-entrypoint-initdb.d/ run automatically, alphabetically, only on a first boot against an empty data volume — that's how init.sql bootstraps the schema without a separate migration step for a first run.

PostgreSQL & the pg connection pool

Use node-postgres (pg) directly for full SQL control, or as the driver underneath an ORM/query builder. Either way, connect through a pool, never a single client — a pool hands out reusable connections instead of paying TCP + auth handshake cost per request.

src/config/db.js
const { Pool } = require('pg');

const pool = new Pool({
  host: process.env.DB_HOST,
  port: process.env.DB_PORT || 5432,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  max: 10,                     // max simultaneous connections in the pool
  idleTimeoutMillis: 30000,    // close idle clients after 30s
  connectionTimeoutMillis: 5000,
});

pool.on('error', (err) => {
  // fires for errors on *idle* clients — a crashed connection
  // sitting in the pool, not a query-time error
  console.error('Unexpected idle client error', err);
  process.exit(1);
});

module.exports = pool;
db/init.sql
CREATE TABLE IF NOT EXISTS users (
  id          SERIAL PRIMARY KEY,
  name        VARCHAR(120) NOT NULL,
  email       VARCHAR(160) NOT NULL UNIQUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
Always parameterizeNever string-concatenate values into SQL. pool.query('SELECT * FROM users WHERE id = $1', [id]) — the $1 placeholder is filled by the driver, which escapes it. Template-literal SQL is the #1 way this stack gets SQL-injected.
05

Express app skeleton

Split app.js (the Express instance and middleware wiring — importable by tests without opening a port) from server.js (the thing that actually calls .listen()).

src/app.js
const express = require('express');
const helmet = require('helmet');
const cors = require('cors');
const morgan = require('morgan');

const userRoutes = require('./routes/user.routes');
const errorHandler = require('./middlewares/errorHandler');
const ApiError = require('./utils/ApiError');

const app = express();

app.use(helmet());                 // sensible security headers
app.use(cors());                    // CORS policy — lock this down in prod
app.use(express.json());            // parse JSON bodies
app.use(morgan('dev'));             // request logging

app.use('/api/users', userRoutes);

// unmatched routes → 404, funneled into the same error pipeline
app.use((req, res, next) => next(new ApiError(404, 'Route not found')));

app.use(errorHandler);              // must be registered LAST

module.exports = app;
src/server.js
const app = require('./app');
const PORT = process.env.PORT || 3000;

app.listen(PORT, () => console.log(`API listening on :${PORT}`));

CRUD routes & controllers

src/routes/user.routes.js
const router = require('express').Router();
const ctrl = require('../controllers/user.controller');
const validate = require('../middlewares/validate');
const { createUserSchema, updateUserSchema } = require('../validators/user.schema');

router.get('/', ctrl.listUsers);
router.get('/:id', ctrl.getUser);
router.post('/', validate(createUserSchema), ctrl.createUser);
router.put('/:id', validate(updateUserSchema), ctrl.updateUser);
router.delete('/:id', ctrl.deleteUser);

module.exports = router;
src/services/user.service.js
const pool = require('../config/db');

exports.findAll = async () => {
  const { rows } = await pool.query(
    'SELECT id, name, email, created_at FROM users ORDER BY id'
  );
  return rows;
};

exports.findById = async (id) => {
  const { rows } = await pool.query(
    'SELECT id, name, email, created_at FROM users WHERE id = $1',
    [id]
  );
  return rows[0] || null;
};

exports.create = async ({ name, email }) => {
  const { rows } = await pool.query(
    `INSERT INTO users (name, email) VALUES ($1, $2)
     RETURNING id, name, email, created_at`,
    [name, email]
  );
  return rows[0];
};

exports.update = async (id, { name, email }) => {
  const { rows } = await pool.query(
    `UPDATE users SET name = $1, email = $2, updated_at = now()
     WHERE id = $3
     RETURNING id, name, email, updated_at`,
    [name, email, id]
  );
  return rows[0] || null;
};

exports.remove = async (id) => {
  const { rowCount } = await pool.query('DELETE FROM users WHERE id = $1', [id]);
  return rowCount > 0;
};
src/controllers/user.controller.js
const service = require('../services/user.service');
const ApiError = require('../utils/ApiError');
const ApiResponse = require('../utils/ApiResponse');

// asyncHandler removes the need for try/catch in every controller —
// it forwards any rejected promise straight to next(err)
const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

exports.listUsers = asyncHandler(async (req, res) => {
  const users = await service.findAll();
  res.json(new ApiResponse(200, users));
});

exports.getUser = asyncHandler(async (req, res) => {
  const user = await service.findById(req.params.id);
  if (!user) throw new ApiError(404, 'User not found');
  res.json(new ApiResponse(200, user));
});

exports.createUser = asyncHandler(async (req, res) => {
  const user = await service.create(req.body);
  res.status(201).json(new ApiResponse(201, user, 'User created'));
});

exports.updateUser = asyncHandler(async (req, res) => {
  const user = await service.update(req.params.id, req.body);
  if (!user) throw new ApiError(404, 'User not found');
  res.json(new ApiResponse(200, user, 'User updated'));
});

exports.deleteUser = asyncHandler(async (req, res) => {
  const deleted = await service.remove(req.params.id);
  if (!deleted) throw new ApiError(404, 'User not found');
  res.status(204).send();
});
Why RETURNING mattersPostgres's RETURNING clause hands back the row you just wrote in the same round trip — no separate SELECT needed after an INSERT/UPDATE. One query instead of two, and no race window between the write and the read-back.

Validation with Joi

Validate at the edge, before any DB call — malformed input should never reach a query. A generic middleware factory keeps this a one-line addition per route.

src/validators/user.schema.js
const Joi = require('joi');

exports.createUserSchema = Joi.object({
  name: Joi.string().trim().min(2).max(120).required(),
  email: Joi.string().trim().email().required(),
});

exports.updateUserSchema = Joi.object({
  name: Joi.string().trim().min(2).max(120).required(),
  email: Joi.string().trim().email().required(),
});
src/middlewares/validate.js
const ApiError = require('../utils/ApiError');

module.exports = (schema) => (req, res, next) => {
  const { error, value } = schema.validate(req.body, {
    abortEarly: false,   // collect every violation, not just the first
    stripUnknown: true,  // drop fields the schema doesn't define
  });

  if (error) {
    const details = error.details.map((d) => d.message);
    return next(new ApiError(400, 'Validation failed', details));
  }

  req.body = value; // sanitized/coerced payload
  next();
};
abortEarly: falseWithout this flag Joi stops at the first invalid field. A client fixing one error at a time against a slow feedback loop is a worse experience than getting the full list of what's wrong in one response.
08

Centralized error handling

One error-handling middleware, registered last, is the single place that decides HTTP status and response shape for every failure — thrown, rejected, or next(err)'d — anywhere in the request lifecycle.

src/utils/ApiError.js
class ApiError extends Error {
  constructor(statusCode, message, details = []) {
    super(message);
    this.statusCode = statusCode;
    this.details = details;
    this.isOperational = true; // distinguishes "expected" errors from bugs
    Error.captureStackTrace(this, this.constructor);
  }
}

module.exports = ApiError;
src/middlewares/errorHandler.js
const ApiError = require('../utils/ApiError');

module.exports = (err, req, res, next) => {
  let error = err;

  // Postgres unique-violation → surface as a clean 409, not a 500
  if (err.code === '23505') {
    error = new ApiError(409, 'Resource already exists');
  } else if (!(error instanceof ApiError)) {
    // unexpected/programmer error — log full detail, leak nothing to the client
    console.error(err);
    error = new ApiError(500, 'Internal server error');
  }

  res.status(error.statusCode).json({
    success: false,
    message: error.message,
    ...(error.details?.length ? { details: error.details } : {}),
    ...(process.env.NODE_ENV !== 'production' ? { stack: err.stack } : {}),
  });
};
Four-argument signature is load-bearingExpress only recognizes a middleware as an error handler if it declares exactly (err, req, res, next) — four parameters, in that order, even though next is unused. Drop to three and it's treated as a normal middleware and silently never called on error.

Standardized response envelope

Every success response follows the same shape, so client code never branches on which endpoint it called.

src/utils/ApiResponse.js
class ApiResponse {
  constructor(statusCode, data, message = 'Success') {
    this.statusCode = statusCode;
    this.success = statusCode < 400;
    this.message = message;
    this.data = data;
  }
}

module.exports = ApiResponse;
Example success
{
  "statusCode": 201,
  "success": true,
  "message": "User created",
  "data": { "id": 4, "name": "Asha Rao", "email": "asha@example.com" }
}
Example failure (from the error handler)
{
  "success": false,
  "message": "Validation failed",
  "details": ["\"email\" must be a valid email"]
}

Config & secrets

.env
NODE_ENV=development
PORT=3000
DB_HOST=db
DB_PORT=5432
DB_USER=appuser
DB_PASSWORD=apppass
DB_NAME=appdb

Load and validate env vars at boot rather than trusting them silently — a missing DB_PASSWORD should fail fast at startup, not three requests in when the pool tries to connect.

// src/config/env.js
const required = ['DB_HOST', 'DB_USER', 'DB_PASSWORD', 'DB_NAME'];
const missing = required.filter((k) => !process.env[k]);
if (missing.length) {
  throw new Error(`Missing required env vars: ${missing.join(', ')}`);
}
.env in .dockerignore and .gitignoreThe Compose file's env_file: .env injects secrets at container start — the file itself should never be baked into the image (.dockerignore) or committed (.gitignore). Ship a .env.example with placeholder values instead.
11

Security checklist

  • Parameterized queries only — never interpolate user input into SQL strings.
  • helmet() — sets X-Content-Type-Options, X-Frame-Options, and other headers that cost nothing to enable.
  • Explicit CORS origin in production — cors() with no options reflects any origin; pass { origin: 'https://yourapp.com' }.
  • Rate limiting — express-rate-limit on write endpoints at minimum, to blunt brute-force and scraping.
  • Least-privilege DB role — the app's Postgres user shouldn't have SUPERUSER or the ability to DROP tables it doesn't own.
  • Don't leak stack traces in production responses — the error handler above gates stack behind NODE_ENV !== 'production'.
  • Validate and constrain at the DB layer — Joi catches bad input; a UNIQUE constraint and NOT NULL catch the race conditions Joi structurally can't (two concurrent requests both passing validation for the same email).

Raw pg vs a query builder vs a full ORM

The tutorial's stack uses raw pg for full control and zero abstraction cost — worth knowing what you're trading away.

Data-access layer options for this stack
node-postgres (pg)KnexSequelize / Prisma
SQL controlfull — you write itnear-full, builder syntaxabstracted away
Learning curvejust SQLbuilder API + SQLORM-specific concepts
Migrationshand-rolled / external toolbuilt inbuilt in
Boilerplate for simple CRUDmostmediumleast
Complex joins / window functionsnaturalnaturaloften fights the ORM
Type safety (TS)manual typingpartialPrisma generates types

Raw pg is the right default when the query set is small and known (exactly this CRUD-API case) and you want zero surprise about what SQL actually runs. Reach for Prisma or Sequelize once the schema and relations grow past what you want to hand-write repeatedly, or once a team needs migration tooling and generated types more than it needs query-level control.
