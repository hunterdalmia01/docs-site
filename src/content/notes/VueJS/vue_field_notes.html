Vue.js Field Notes

Vue, from "what is a framework" to shipping in production

A complete working reference combining the official interactive tutorial with the full Vue.js Guide — every page from Introduction through Security. Sections follow the guide's own structure: Essentials, Components In-Depth, Reusability, Built-in Components, Scaling Up, and Best Practices. Code samples pair the Options API and Composition API wherever the guide teaches both.

Sources: vuejs.org/guide/introduction.html and vuejs.org/tutorial

01

Introduction

What Vue is, and the two ways to write it

Vue is a JavaScript framework for building user interfaces, built around a declarative, component-based programming model: describe what the UI should look like for a given state, and Vue renders and updates the DOM efficiently as that state changes. It scales from a single <script> tag enhancing a static page up to full single-page applications with routing, state management, and a build pipeline.

Two API styles cover the same underlying engine:

  • Options API — a component is an object with data, methods, computed, and lifecycle-hook options; this refers to the component instance inside them.
  • Composition API — a component uses imported functions (ref, reactive, computed, onMounted, ...) inside a setup() function or, more commonly, a <script setup> block — better suited to extracting and reusing logic across components (see Composables).
Both styles are fully supported and interoperable; the guide (and these notes) show both side by side rather than picking one as "correct." Composition API is generally preferred for larger, more complex components and for logic reuse; Options API keeps things simple and structured for smaller ones.

Vue components can be authored as Single-File Components (.vue files, compiled by a build step) or with plain JavaScript objects — no build step required, useful for progressively enhancing existing HTML.

Quick start

Two on-ramps: scaffolded project or CDN
# scaffolds a Vite-powered project, prompts for TS/Router/Pinia/testing
npm create vue@latest

cd <project-name>
npm install
npm run dev

For no-build, drop-in usage — enhancing a static page without a bundler:

<script src="https://unpkg.com/vue@3/dist/vue.global.js"></script>

<div id="app">{{ message }}</div>

<script>
  const { createApp } = Vue
  createApp({
    data() { return { message: 'Hello Vue!' } }
  }).mount('#app')
</script>

create-vue (the official scaffolding tool, run via npm create vue@latest) is built on Vite and is the recommended starting point for any real application. The official Vue Devtools browser extension is worth installing early — it inspects component trees, reactive state, events, and routing/store state live.

Essentials
03

Creating a Vue application

createApp, mounting, and app-level config
import { createApp } from 'vue'
import App from './App.vue'

const app = createApp(App)

app.mount('#app')

Every app needs a root component — everything else nests inside it. createApp() returns an application instance, which exposes app-level configuration before mounting: app.component() and app.directive() for global registration, app.use() for plugins, and app.config.errorHandler for a global error hook.

Multiple independent app instances can coexist on one page, each with its own mount point and configuration — useful when Vue is only powering isolated widgets on an otherwise server-rendered page.
04

Template syntax

Interpolation, directives, arguments, modifiers
<!-- text interpolation -->
<span>{{ msg }}</span>

<!-- raw HTML (only for trusted content — see Security) -->
<p v-html="rawHtml"></p>

<!-- directive, argument, and modifier -->
<a v-on:click.prevent="doSomething">link</a>

<!-- dynamic argument -->
<a v-bind:[attributeName]="url">link</a>

Anatomy of a directive: v-on:click.prevent="doSomething" — the part after the colon is the argument (which event, which attribute), and anything after a dot is a modifier that tweaks how the directive binds. Arguments can themselves be dynamic, computed from an expression in square brackets. Inside mustaches and directive values, only single JavaScript expressions are allowed — not statements or control flow.

05

Reactivity fundamentals

ref() vs reactive()
import { ref, reactive } from 'vue'

const count = ref(0)        // wraps any value type; access/mutate via .value in JS
count.value++

const state = reactive({ count: 0 })  // deep-reactive proxy of an object
state.count++

ref() can hold any value type (primitives included) and needs .value in JavaScript — but templates unwrap it automatically. reactive() only works on objects/arrays/Maps/Sets, returns a Proxy, and is deeply reactive (nested objects are automatically wrapped too).

Reactive limitations to remember: destructuring a property off a reactive() object loses its reactivity connection (use toRefs() to destructure safely); reassigning the whole object (state = reactive({...})) breaks the original reference. ref() doesn't have either problem, which is why many codebases default to ref() even for objects.

DOM updates from a state change are asynchronous and batched — Vue queues them and flushes once per "tick." To act on the DOM right after an update, await nextTick().

06

Computed properties

Cached derived state, and when it can be writable
const fullName = computed({
  get() {
    return `${firstName.value} ${lastName.value}`
  },
  set(newValue) {
    ;[firstName.value, lastName.value] = newValue.split(' ')
  }
})

A computed property caches its result and only recomputes when a tracked dependency changes — cheaper than a method call re-run on every render. Passing a plain getter function creates a read-only computed; passing { get, set } creates a writable one.

Getters should be pure: no async work, no mutating other state, no DOM access inside a computed getter — it may run any number of times and should have no side effects.
07

Class and style bindings

Object and array syntax, merged with component classes
<div
  :class="[isActive ? 'active' : '', errorClass]"
  :class="{ active: isActive, 'text-danger': hasError }"
></div>

<div :style="[baseStyles, overridingStyles]"></div>

Array syntax applies a list of classes/style objects together. When :class or :style is used on a component tag, Vue merges it with the classes/styles the component's own root element already declares, rather than overwriting them.

08

Conditional rendering

v-if vs v-show, and <template> groups
<template v-if="ok">
  <!-- group multiple elements under one v-if, with no extra wrapper -->
  <h1>Title</h1>
  <p>Paragraph</p>
</template>

v-if is "real" conditional rendering — it destroys and recreates the element (and any component's local state) on toggle. v-show always renders the element and just toggles CSS display, so state and DOM structure survive toggles cheaply.

By default, Vue reuses matching elements across a v-if/v-else toggle for efficiency (e.g. an <input> keeps focus and typed value). Give elements distinct :keys if that reuse would be wrong for your case.
09

List rendering

Iterating arrays, objects, and ranges
<li v-for="(item, index) in items" :key="item.id">{{ index }} - {{ item.text }}</li>
<li v-for="(value, key) in myObject" :key="key">{{ key }}: {{ value }}</li>
<span v-for="n in 5" :key="n">{{ n }}</span> <!-- 1..5 -->

Vue detects and reacts to array mutation methods (push, pop, splice, sort, reverse, ...) automatically; a method that returns a new array (filter, map) needs its result reassigned back to the reactive reference.

Never combine v-if and v-for on the same element — the guide explicitly discourages it (and it's a lint rule in eslint-plugin-vue). Filter the source list with a computed property first, or move the v-if onto a wrapping <template>.

Event handling

Inline vs method handlers, modifiers, key modifiers
<button @click="count++">Add 1</button>
<button @click="greet('hi', $event)">Greet</button>

<form @submit.prevent="onSubmit">...</form>
<div @click.self="onClickSelf">...</div>
<input @keyup.enter="submit">

.stopevent.stopPropagation()
.preventevent.preventDefault()
.selfOnly trigger if the event's target is this element itself
.onceTrigger at most once
.capture, .passiveMap to the DOM listener's capture/passive options

Form input bindings

v-model modifiers and multi-element forms
<input v-model.lazy="msg">    <!-- sync on change, not every keystroke -->
<input v-model.number="age">   <!-- cast to a Number automatically -->
<input v-model.trim="name">    <!-- strip whitespace -->

<input type="checkbox" v-model="checkedNames" value="Jack">
<select v-model="selected" multiple>
  <option>A</option>
  <option>B</option>
</select>

Binding several checkboxes to the same array automatically pushes/removes each checkbox's value as it's checked/unchecked; a multi-select binds to an array of the selected options' values.

12

Watchers

watch vs watchEffect, deep watching, timing
import { watch, watchEffect } from 'vue'

// explicit source(s) + old/new values
watch(source, (newVal, oldVal) => { /* ... */ })

// watch a nested property inside a reactive object
watch(() => state.someObject.nested, callback, { deep: true })

// runs immediately, and re-runs whenever any reactive dep it read changes
watchEffect(() => {
  console.log(count.value)
})
OptionEffect
immediate: trueRun the callback once right away, not just on the first change
deep: trueWatch every nested property, not just the top-level reference
flush: 'post'Run the callback after Vue's DOM update, so template refs reflect the change

watch is lazy by default (runs only on change) and gives you both old and new values — best for a specific, known source. watchEffect auto-tracks whatever reactive state its function body reads — best when several sources should trigger the same effect and you don't need the previous value. Both return a stop handle: call it, e.g. const stop = watchEffect(...); stop(), to end the watcher manually.

13

Template refs

Refs in loops, function refs, and refs across components
// ref inside v-for — collects into an array, order not guaranteed
const itemRefs = ref([])

<li v-for="item in list" :ref="itemRefs">{{ item }}</li>

A ref attribute can also take a function, called with the element on mount and with null on unmount — useful for full manual control. To access a child component's internals from the parent, the child must explicitly opt in with defineExpose({ ... }); by default a component's internals are private to outside refs.

14

Components basics

Defining, using, and dynamic components
<component :is="currentTab"></component>

<KeepAlive>
  <component :is="currentTab"></component>
</KeepAlive>

<component :is="..."></component> switches between components dynamically by binding to a component object or its registered name. Wrapping it in <KeepAlive> preserves each tab's state across switches instead of destroying and recreating it (see Built-in Components).

DOM template parsing caveat: if a template is written directly in HTML (not inside an SFC or a string template), the browser's own HTML parser runs first and silently rewrites invalid nesting — e.g. a custom component inside a native <ul>/<table> gets hoisted out. Affects in-DOM templates only, not .vue files.

Components in-depth
16

Component registration

Global vs local
// global — available everywhere, but always bundled even if unused
app.component('MyComponent', MyComponent)

// local — import + register per component (or auto-exposed by <script setup>)
import MyComponent from './MyComponent.vue'
export default {
  components: { MyComponent }
}

Local registration is the default recommendation: it keeps the dependency graph explicit and lets a bundler tree-shake unused components. Global registration trades that for convenience on components used nearly everywhere (e.g. a base button or icon set).

17

Props

Validation, casing, and one-way data flow
defineProps({
  title: String,
  likes: { type: Number, default: 0 },
  status: {
    type: String,
    required: true,
    validator: (value) => ['ok', 'error'].includes(value)
  }
})

Props declared in camelCase (greetingMessage) are passed from the parent template in kebab-case (greeting-message) — HTML attributes are case-insensitive, so this convention is required, not stylistic. A prop of type Boolean is cast: the attribute's mere presence, with no value, is treated as true.

Props flow one way, down. Mutating a prop inside the child is flagged by Vue's warning system, because the parent's next re-render can silently overwrite that local change. Copy it into local state (Options: a data() field seeded from the prop; Composition: ref(props.foo)) or derive a computed from it instead.
18

Component events

Declaring and validating emits
const emit = defineEmits({
  submit: (payload) => {
    if (!payload.email) {
      console.warn('submit event missing email')
      return false
    }
    return true
  }
})

emit('submit', { email: 'a@b.com' })

Declaring emits (as an array of names, or an object mapping name to a validator function) documents the component's public event contract and lets Vue warn on typos or bad payloads — the same spirit as prop validation, for the outgoing side.

19

Component v-model

Two-way binding on a custom component
<!-- parent -->
<CustomInput v-model="searchText" />

<!-- desugars to: -->
<CustomInput :model-value="searchText" @update:model-value="searchText = $event" />
// inside CustomInput.vue
const model = defineModel()
// use model.value directly — reading and writing both sync to the parent

defineModel() is sugar (Vue 3.4+) over declaring a modelValue prop plus an update:modelValue emit by hand. Named models — v-model:title="..." — and modifiers on a component v-model both work the same way, just with the corresponding name substituted for modelValue/model-value.

20

Fallthrough attributes

Attributes the parent passes that aren't declared props

Any attribute or listener passed to a component that isn't a declared prop or emit "falls through" automatically onto the component's single root element — e.g. a plain class or id passed to a wrapper component lands on its root <div> without any explicit wiring.

export default {
  inheritAttrs: false // opt out of automatic fallthrough
}
<div class="wrapper">
  <input v-bind="$attrs" />  <!-- forward them explicitly, e.g. onto an inner element -->
</div>
A component with multiple root nodes does not auto-inherit attributes — Vue can't guess which root they belong to, so $attrs must be bound explicitly somewhere in that case.
21

Slots

Named slots, scoped slots, and fallback content
<!-- child: FancyList.vue -->
<slot name="header"></slot>
<slot v-for="item in items" :item="item">{{ item.text }}</slot>

<!-- parent -->
<FancyList>
  <template #header><h2>Results</h2></template>
  <template #default="{ item }">
    <strong>{{ item.text }}</strong>
  </template>
</FancyList>

Named slots (name="header", filled with #header) let a component expose several distinct content areas. Scoped slots pass data from child to parent through the slot itself — bindings on <slot> become the object destructured in #default="{ item }" — the one case where data flows slot-content-ward from child to parent.

22

Provide / inject

Skipping prop drilling through deep trees
// ancestor
import { provide, ref } from 'vue'
const location = ref('North Pole')
provide('location', location) // pass a ref to keep it reactive

// any descendant, any number of levels down
import { inject } from 'vue'
const location = inject('location', 'The Universe' /* default */)

Props work well for one or two levels; beyond that, threading a value through every intermediate component ("prop drilling") gets unwieldy. provide/inject lets an ancestor make a value available to any descendant directly. Provide a ref (not a raw value) to keep the link reactive, and prefer Symbol keys over plain strings in larger apps to avoid key collisions between unrelated features.

23

Async components

Code-splitting a component behind a dynamic import
import { defineAsyncComponent } from 'vue'

const AsyncComp = defineAsyncComponent(() => import('./MyComponent.vue'))

// with loading/error states and delay/timeout tuning
const AsyncCompWithOptions = defineAsyncComponent({
  loader: () => import('./MyComponent.vue'),
  loadingComponent: LoadingSpinner,
  errorComponent: ErrorDisplay,
  delay: 200,
  timeout: 3000
})

defineAsyncComponent wraps a dynamic import() so a bundler (Vite, webpack) splits that component into its own chunk, loaded only when it's actually rendered — standard practice for rarely-visited routes or heavy components (charts, editors) that shouldn't bloat the initial bundle.

Reusability
24

Composables

Extracting and reusing stateful logic
// useMouse.js
import { ref, onMounted, onUnmounted } from 'vue'

export function useMouse() {
  const x = ref(0), y = ref(0)
  function update(event) { x.value = event.pageX; y.value = event.pageY }
  onMounted(() => window.addEventListener('mousemove', update))
  onUnmounted(() => window.removeEventListener('mousemove', update))
  return { x, y }
}

// in a component
const { x, y } = useMouse()

A composable is a plain function that uses Composition API primitives to encapsulate and reuse stateful logic — the Composition API's answer to what mixins tried (and largely failed) to solve, because a composable's return value is explicit rather than merged in behind the scenes. By convention, a composable is named useXxx and any reactive input it takes should be a ref, not a plain value, so it keeps reacting to later changes.

25

Custom directives

Low-level, imperative DOM access as a directive
const vFocus = {
  mounted: (el) => el.focus()
}

// registered locally in <script setup>, used as v-focus
app.directive('highlight', {
  mounted(el, binding) {
    el.style.background = binding.value
  },
  updated(el, binding) {
    el.style.background = binding.value
  }
})

A custom directive is a set of lifecycle hooks (mounted, updated, unmounted, ...) mirroring the component lifecycle, given direct element access. Reach for one only for low-level DOM work that has no clean declarative equivalent (autofocus, a tooltip library integration, a click-outside handler) — most UI logic belongs in a component or composable instead.

26

Plugins

App-wide functionality behind app.use()
const myPlugin = {
  install(app, options) {
    app.config.globalProperties.$translate = (key) => key
    app.component('MyGlobalComponent', MyGlobalComponent)
    app.directive('my-directive', { /* ... */ })
    app.provide('some-value', 42)
  }
}

app.use(myPlugin, { /* options */ })

A plugin is an object with an install(app, options) function (or just that function directly). It's the standard packaging shape for anything that needs to register app-wide — a router, a state-management library, a i18n layer, or a set of globally-available components and directives.

Built-in components
27

Transition

Animating a single element's enter/leave
<Transition name="fade">
  <p v-if="show">hello</p>
</Transition>
.fade-enter-active, .fade-leave-active { transition: opacity 0.3s ease; }
.fade-enter-from, .fade-leave-to { opacity: 0; }

Wrapping a single conditionally-rendered element (v-if/v-show) in <Transition> auto-applies a set of CSS classes at each phase of enter/leave (*-enter-from, *-enter-active, *-enter-to, and the mirrored *-leave-* trio), which you style with a normal CSS transition or animation — no animation library required for the common case.

28

TransitionGroup

Animating a list — including reordering
<TransitionGroup name="list" tag="ul">
  <li v-for="item in items" :key="item.id">{{ item.text }}</li>
</TransitionGroup>

Unlike <Transition>, this renders an actual wrapper element (tag="ul") and can animate multiple items at once — including a v-move class applied during reordering, powered by the FLIP technique, so items sliding to a new position animate smoothly rather than jumping.

29

KeepAlive

Caching inactive component instances
<KeepAlive :include="['TabA', 'TabB']" :max="10">
  <component :is="activeTab" />
</KeepAlive>

Wrapping a dynamic component in <KeepAlive> keeps its instance (and state — scroll position, form input, fetched data) alive in memory when it's switched away from, instead of destroying it. include/exclude filter which named components get cached; max caps how many instances stay resident (LRU eviction beyond that). Cached components get activated/deactivated hooks instead of a second mount/unmount cycle.

30

Teleport

Rendering outside the component's DOM position
<Teleport to="body">
  <div class="modal">...</div>
</Teleport>

A component's template usually renders exactly where it sits in the tree — a problem for a modal or tooltip nested deep inside a positioned/overflow-hidden ancestor, where CSS z-index/overflow fights get ugly. <Teleport> moves the rendered DOM to a different location in the document (commonly straight under <body>) while keeping it logically part of the same component — it still has access to the parent's data and still participates in the parent's event flow.

31

Suspense

Coordinating nested async dependencies (experimental)
<Suspense>
  <template #default>
    <AsyncComponentWithAwaitInSetup />
  </template>
  <template #fallback>
    Loading...
  </template>
</Suspense>

<Suspense> shows fallback content while one or more descendant components with an async setup() (e.g. awaiting a fetch before rendering) are still resolving, then swaps to the real content once every one of them settles.

The guide marks <Suspense> as an experimental feature — its API isn't fully stable and may still change between minor versions. Confirm current status against the docs before depending on it in production.

Single-file components

The anatomy of a .vue file
<template>
  <p class="greeting">{{ greeting }}</p>
</template>

<script setup>
import { ref } from 'vue'
const greeting = ref('Hello World!')
</script>

<style scoped>
.greeting { color: red; font-weight: bold; }
</style>

An SFC (.vue file) colocates a component's template, logic, and styling in one file, compiled by build tooling into a plain JavaScript module. <style scoped> auto-generates unique attributes so those rules apply only within this component, without leaking globally.

Tooling

Vite, the devtools extension, and TypeScript support
  • Vite — the official, recommended build tool: fast dev-server cold starts via native ES modules, and a Rollup-based production build. create-vue scaffolds a Vite project by default.
  • Vue Devtools — a browser extension for inspecting the live component tree, reactive state, emitted events, and (if present) router/Pinia state.
  • IDE support — the Vue - Official VS Code extension (formerly Volar) provides .vue syntax highlighting, TypeScript type-checking inside SFCs, and template auto-completion.
  • TypeScript — supported throughout; defineProps<{ msg: string }>() and defineEmits<{ change: [id: number] }>() give fully typed props/emits without a runtime schema object.

Routing

Vue Router — the official client-side router
import { createRouter, createWebHistory } from 'vue-router'

const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', component: Home },
    { path: '/users/:id', component: UserDetail, props: true }
  ]
})

app.use(router)
<RouterLink to="/about">About</RouterLink>
<RouterView />

For a single-page application, Vue Router maps URL paths to components, handles the browser back/forward history, and supports nested routes, route params, guards (beforeEnter, router.beforeEach), and lazy-loaded route components via dynamic import().

State management

From local state to Pinia
import { defineStore } from 'pinia'

export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0 }),
  getters: { double: (state) => state.count * 2 },
  actions: { increment() { this.count++ } }
})

// in a component
const counter = useCounterStore()
counter.increment()

Pinia is the official state-management library, replacing the earlier Vuex. Reach for a shared store when several unrelated components need the same state and provide/inject or prop-passing becomes awkward — but plain reactive state in a composable is often enough for small to mid-sized apps, and the guide explicitly recommends not reaching for a store library by default.

Server-side rendering

SSR concepts, and reaching for Nuxt

Server-side rendering executes the app on the server per-request to produce full HTML up front — better initial paint and SEO than a purely client-rendered SPA, since crawlers and slow connections see real content immediately. The client then "hydrates" that HTML, attaching interactivity without re-rendering from scratch.

Nuxt is the standard way most teams reach SSR with Vue in practice — it wraps Vue's lower-level SSR API with routing, data-fetching conventions, and deployment tooling, the way the guide frames "build SSR yourself" as the manual path and Nuxt as the recommended one for real projects.
Best practices
38

Production deployment

Building for production correctly
npm run build   # emits a minified, production-mode bundle to dist/

A production build strips development-only warnings, minifies output, and disables the Options/Composition API's dev-mode reactivity warnings — always deploy the built bundle, never the dev server. If the app is only partially interactive on an otherwise static/server-rendered page, only load Vue where it's actually needed rather than shipping the full framework for a widget or two.

39

Performance

v-once, v-memo, and general bundle hygiene
<div v-once>{{ expensiveStaticContent }}</div>

<div v-memo="[valueA, valueB]">
  <!-- skips re-render unless valueA or valueB actually changed -->
</div>
  • v-once — renders an element/component tree once and skips it on every future update; for content that genuinely never changes after the first render.
  • v-memo — memoizes a template subtree against a dependency array, useful for very large v-for lists where most rows don't change between renders.
  • Virtualize long lists (e.g. with vue-virtual-scroller) rather than rendering thousands of DOM nodes at once.
  • Lazy-load routes and heavy components via defineAsyncComponent / route-level dynamic imports to keep the initial bundle small.
40

Accessibility

Semantic HTML, focus, and ARIA basics
  • Prefer semantic elements (<button>, <nav>, <label>) over a generic <div> with a click handler — screen readers and keyboard navigation rely on native semantics.
  • Manage focus explicitly around route changes and modals — e.g. move focus into a <Teleport>-rendered modal on open, and back to the trigger element on close.
  • Add ARIA attributes only to fill a real gap semantic HTML can't cover; an ARIA role on the wrong element is often worse than none at all.
  • Respect prefers-reduced-motion in <Transition>/<TransitionGroup> CSS for users sensitive to motion.
41

Security

Where Vue apps are actually exposed to XSS
v-html renders raw, unescaped HTML. Passing any user-controllable string to it is a direct XSS vector — only ever use it with content you trust completely (e.g. sanitized CMS output, not raw user input).

Text interpolation ({{ }}) is always escaped and safe by default — the risk is specifically v-html, dynamically constructed :href/:src values that could resolve to a javascript: URL, and any templates compiled at runtime from untrusted, user-supplied strings (avoid runtime template compilation from user input entirely). Third-party components and plugins execute with the same trust level as your own code — audit dependencies the same way you would any other code with DOM access.
